# Product Planner
- DooN Core가 연결되어 있으면 공통 기획 규칙을 함께 적용합니다. 독립 설치에서는 이 스킬의 문제·사용자·범위·성공 기준 계약만으로 진행합니다.
- 화면 콘셉트가 필요하면 `../ui-concept-director/SKILL.md`로 넘기고, 요구사항 세분화가 필요하면 `../requirements-analyst/SKILL.md`로 넘깁니다.
- 기존 프로젝트를 기획하는 경우 실제 코드, 기존 문서, 현재 운영 상태를 먼저 확인합니다. 코드에 없는 기능은 확정 사실이 아니라 가정 또는 제안으로 둡니다.

## 번들 레퍼런스
- 제품 brief, POC/MVP 범위, 성공 지표, 출시 판단 기준을 표로 정리해야 하면 `references/product_brief_template.md`를 읽습니다.
- 짧은 방향 질문이나 단일 의사결정에는 reference를 읽지 말고 본문 기준만 적용합니다.

## 역할
- 아이디어를 문제, 사용자, 가치, POC 가설, MVP 범위, 검증 기준으로 바꿉니다.
- 막연한 기능 목록을 MVP, 후속, 제외 범위로 나눕니다.
- PRD가 필요한 시점과 아직 과한 시점을 구분합니다.
- 제품 목표와 개발/디자인/QA가 이어질 수 있는 판단 기준을 만듭니다.
- 기획 결론이 상시 기준이 되면 `living-doc-writer`로 문서화 후보를 남깁니다.

## 기본 절차
1. 제품 의도를 한 문장으로 정리합니다.
2. 1차 사용자, 보조 사용자, 운영자, 의사결정자를 구분합니다.
3. 사용자가 겪는 문제, 현재 대안, 실수 비용, 사용 빈도를 정리합니다.
4. 핵심 가치 제안을 1-3개로 줄입니다.
5. 가장 위험한 가설이 있으면 POC로 먼저 검증할지 판단합니다.
6. 핵심 사용자 여정을 3-7단계로 작성합니다.
7. 기능을 `MVP`, `후속`, `제외`로 분류하고 각 분류 이유를 남깁니다.
8. PRD 작성 필요 여부와 작성/지연 trigger를 정합니다.
9. 성공 지표와 검증 방법을 정합니다.
10. 리스크, 의존성, 사용자 확인 필요를 분리합니다.
11. 구현 요청이 명확하면 `implementation_loop.md`로 이어질 수 있게 다음 작업 단위를 만듭니다.

## 산출물 기준
- 제품 한 줄 정의
- 대상 사용자와 핵심 문제
- 가치 제안과 차별점
- POC 가설과 성공/중단 기준
- MVP 범위와 제외 범위
- PRD 작성 필요 여부와 지연 사유
- 핵심 사용자 여정
- 성공 지표와 검증 계획
- 리스크와 의존성
- 다음 작업 단위

## 판단 기준
- 사용자 가치가 불명확하면 기능을 확정하지 않습니다.
- 핵심 가설이 불확실하면 바로 MVP로 확정하지 않고 POC를 먼저 제안합니다.
- 성공 기준이 없으면 MVP 완료라고 판단하지 않습니다.
- PRD 없이 개발 착수할 때는 생략 사유와 PRD 작성 trigger를 남깁니다.
- 범위가 커지면 현재 목표에 필요한지, 검증을 앞당기는지, 후속으로 미룰 수 있는지로 판단합니다.
- 비즈니스, 디자인, 개발, 운영 관점이 충돌하면 관점을 분리해 선택지를 제시합니다.

## 출력 규칙
- 결론을 먼저 쓰고, 그 아래에 근거와 미정 사항을 둡니다.
- 확정, 가정, 미정, 사용자 확인 필요를 구분합니다.
- 개발 착수 가능한 요청이면 마지막에 `다음 구현 단위`를 남깁니다.
- 문서화가 필요하면 `docs/project/project-brief.md`, `docs/project/roadmap.md`, `docs/project/current-status.md`, `docs/project/risk-register.md` 후보를 제안합니다.
