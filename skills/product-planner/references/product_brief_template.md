점검:

- 사용자가 직접 겪는 문제와 운영자가 해결하고 싶은 문제가 섞이지 않았는지 확인한다.
- “있으면 좋음”과 “없으면 실패함”을 분리한다.
- 사용 빈도와 실수 비용 중 하나라도 높으면 MVP 우선순위 후보로 본다.

|---|---|---|---|---|---|
| H1 |  | high/medium/low | POC/interview/prototype/log |  |  |

POC가 필요한 경우:

- 핵심 사용자가 실제로 이 문제를 자주 겪는지 불확실하다.
- 기술 구현 가능성보다 행동 변화 가능성이 더 큰 위험이다.
- MVP를 만들면 시간이 많이 들지만 작은 실험으로 확인할 수 있다.

분류 기준:

- MVP: 핵심 가설 검증이나 첫 사용자 가치에 직접 필요하다.
- 후속: 가치가 있지만 첫 검증에는 없어도 된다.
- 제외: 현재 문제와 직접 연결되지 않거나 운영 비용이 큰 기능이다.

## 7. 다음 작업 단위

- 기획 확정이 필요하면 `requirements-analyst`로 요구사항 표를 만든다.
- 화면 구조가 필요하면 `information-architect`로 화면 책임과 navigation을 잡는다.
- 시각 방향이 필요하면 `ui-concept-director` 또는 `design-generalist`로 넘긴다.
- 개발 착수가 가능하면 구현 단위를 기능, 화면, API, 데이터, QA 기준으로 나눈다.
