# 상시 문서 작성기

- 문서 본문은 한국어로 작성합니다. 코드 식별자, API 이름, 파일 경로, 명령어, 로그, 외부 고유명사는 원문을 유지할 수 있지만 해설과 요약은 한국어로 둡니다.
- 문서를 쓰기 전에 문서 루트를 결정합니다. 사용자가 별도 경로를 주지 않았다면 기존 `docs/`를 우선 사용하고, 없으면 `docs/`를 기본값으로 삼습니다.
- 문서 루트에 `README.md`가 있으면 이를 유지 문서의 manifest로 취급합니다.
- manifest가 없거나 비어 있으면 `references/docs_readme_template.md`를 불러와 시작 템플릿으로 사용합니다.
- 기존 코드가 있는 주제는 반드시 소스 코드에서 사실을 검증합니다. API, 엔티티, 필드, 흐름, 요구사항을 지어내지 않습니다.
- 아직 코드가 없는 기획 단계에서는 사용자 발화, 회의 메모, 첨부 자료, 기존 문서를 근거로 삼고 `확정`, `가정`, `미정`, `사용자 확인 필요`를 분리합니다.
- 하네스 산출물을 입력으로 받으면 `references/harness_living_doc_bridge.md`를 읽고, 회의별 의견 원문이 아니라 오케스트레이터가 종합한 결론과 채택된 deliverable만 최신 상시 문서로 승격합니다.
- 문서는 미래 독자가 갱신하기 쉽도록 범위, 소유 영역, 관련 코드 경로, 최종 확인일을 드러냅니다.
- 넓은 문서 요청에서는 목적과 독자가 실제로 필요로 하는 문서 구성을 먼저 정합니다. 하나의 문서로 충분하면 한 파일로 작성하고, 갱신 주기·소유자·용도가 갈릴 때만 문서를 분리합니다.
- 날짜 기준 분석·ADR·포스트모템은 `snapshot-report-writer`, 실제 화면을 클릭하며 탐색하는 인터랙티브 웹 가이드는 `service-guide-builder`로 넘깁니다. 정적 화면별 사용 설명서는 이 스킬에서 다룹니다.
- 회의록 자체는 시점 기록에 가깝습니다. 사용자가 회의록 생성을 명시하지 않았다면 회의록을 새로 만들지 말고, 제공된 회의 내용이나 아이디어를 상시 문서의 입력 자료로 사용합니다.

## 프리앰블

- 산출물이 상시 유지 문서인지, 시점성 분석 보고서인지 구분합니다. 후자라면 `../snapshot-report-writer/SKILL.md`가 더 적합할 수 있습니다.
- 작업이 `기획`, `의사결정`, `진행 상태`, `운영/배포`, `온보딩/인수인계`, `QA/테스트`, `데이터/보안/정책`, `디자인 시스템/콘텐츠`, `비즈니스/성과`, `문서 운영`, `신규 단일 문서 작성`, `기존 문서 갱신` 중 무엇인지 먼저 분류합니다.
- 넓은 문서 요청이면 먼저 `references/document_purpose_router.md`를 읽고, 상시 문서로 다룰 목적과 만들 문서군을 정합니다.
- 기획 요청이면 `references/document_intake_router.md`를 읽고, 그 결과에 따라 아래 reference를 추가로 읽습니다.
  - 아이디어 기획: `references/idea_planning_package.md`
  - 디자인 기획: `references/design_planning_package.md`
  - 개발 착수 기획: `references/planning_document_package.md`
- 기획 외 문서군, 여러 문서군이 섞인 요청, 기존 프로젝트 current docs 정리는 `references/living_document_package_matrix.md`를 읽습니다.
- 하네스 회의 결과를 문서화하거나 `publish/harness/` 경로를 입력으로 받으면 `references/harness_living_doc_bridge.md`를 읽습니다.
- 질문 게이트나 품질 기준이 필요하면 `references/requirement_question_gate.md`, `references/document_quality_standards.md`를 읽고 따릅니다.
- 단일 문서 요청이라도 요구사항, 화면, 디자인, 기술 설계, QA처럼 빠지기 쉬운 항목이 있으면 `references/document_quality_standards.md`를 읽고 필수 섹션을 확인합니다.

## 질문 게이트

- 문서 작성 전에 현재 요청이 아이디어 검토인지, 디자인 방향 탐색인지, 개발 착수인지 먼저 판별합니다.
- 개발 목적이 불명확하면 기술 설계, API, DB, QA 문서로 바로 넘어가지 않습니다.
- 디자인 방향이 불명확하면 개발 착수 문서 전에 디자인 후보와 UX 포지셔닝을 먼저 만듭니다.
- 요구사항, 화면, 디자인, 기술, 일정, QA, 운영, 보안, 데이터 보존, 사용자 공개 정책, 성과 측정에 영향을 주는 미정 사항을 먼저 추립니다.
- 플랫폼, 대상 사용자, POC 필요 여부, MVP 범위, PRD 상태, 인증/권한, 결제/과금, 핵심 데이터, 외부 연동, 디자인 방향, 배포 환경, 운영 주체, 개인정보/보안 제약, 일정 제약처럼 선택에 따라 문서 내용이 크게 달라지는 항목은 조용히 가정하지 않습니다.
- 중요한 선택지가 여러 개면 2-3개의 대안을 제시하고 추천안을 표시한 뒤 사용자에게 확인합니다.
- 한 번에 묻는 질문은 핵심 5개 안팎으로 묶습니다. 답변이 없어도 진행 가능한 낮은 위험 항목은 문서의 `가정` 또는 `미정` 섹션에 남깁니다.
- 질문 게이트를 통과하기 전에는 요구사항 정의서, 디자인 확정안, 기술 설계서를 확정 문서처럼 쓰지 않습니다.

## 작업 절차

1. 사용자 요청과 현재 프로젝트 상태를 기준으로 작업 유형과 문서 루트를 확정합니다.
2. 문서 루트의 `README.md` manifest를 읽습니다. 없거나 비어 있으면 `references/docs_readme_template.md`로 생성합니다.
3. 넓은 문서 요청이면 `references/document_purpose_router.md` 기준으로 문서 목적을 판별합니다.
4. 판별 결과가 기획이면 `references/document_intake_router.md` 기준으로 아이디어, 디자인, 개발 착수 중 현재 단계를 판별합니다.
5. 하네스 회의 결과가 입력이면 `references/harness_living_doc_bridge.md` 기준으로 source meeting, deliverable, target living docs root를 확정합니다.
6. 판별된 목적과 단계에 맞는 reference를 읽고 필요한 최소 문서 세트를 정합니다. reference의 패키지는 선택지이지 모든 파일을 만드는 의무가 아닙니다.
   - 기획: `idea_planning_package.md`, `design_planning_package.md`, `planning_document_package.md`
   - 기획 외 상시 문서: `living_document_package_matrix.md`
7. 질문 게이트가 필요한 미정 사항을 확인합니다. 치명적인 미정 사항이 있으면 먼저 질문하고, 그렇지 않으면 문서에 `가정`과 `미정`을 분리해 진행합니다.
8. 기존 프로젝트나 구현된 기능을 문서화하는 경우 관련 소스 파일, 설정, 테스트, 기존 문서를 읽어 사실을 확인합니다.
9. 문서 루트 아래 대상 파일을 작성하거나 갱신합니다. 기존 문서에 통합할 수 있으면 그 파일을 갱신합니다.
10. 문서 안에 범위, 근거 자료, 확정 사항, 가정, 미정 사항, 관련 코드/문서, 갱신 트리거, 검증 방법을 남깁니다.
11. manifest를 사용 중이라면 해당 항목의 `(최종 갱신일: YYYY-MM-DD)`를 갱신합니다.
12. 하네스 문서 승격이면 `30_artifacts/living_docs/README.md`와 `30_artifacts/artifact_index.md`에도 출처 회의와 상태를 반영합니다.
13. 사용자가 PDF 저장을 명시적으로 요청하면, 갱신한 `.md`와 같은 폴더에 같은 basename의 `.pdf`도 함께 저장합니다.

## 검증

- 문서에 적은 API, 경로, 필드, 상태 전이, 예시 값이 실제 코드와 맞는지 다시 대조합니다.
- 가정이 필요한 항목은 확정 사실처럼 쓰지 말고 `가정` 또는 `미정`으로 분리합니다.
- 문서 수보다 요청의 성공 기준과 갱신 가능성을 확인합니다. 단일 파일이 필요한 내용을 충분히 담으면 그대로 완료하고, 서로 다른 독자·소유자·갱신 주기가 섞였을 때만 분리합니다.
- 아이디어 기획에서는 문제, 사용자, 가치, 가설, 검증 계획이 빠지지 않아야 합니다.
- 디자인 기획에서는 디자인 방향 후보, 레퍼런스 분석, UX 포지셔닝, 선택/보류 결정이 빠지지 않아야 합니다.
- 개발 착수 문서에는 POC 필요 여부, MVP 범위, PRD 작성 또는 지연 사유가 있어야 합니다.
- 요구사항 정의서에는 기능별 acceptance criteria와 예외/오류 조건이 있어야 합니다.
- 화면/시나리오 문서에는 빈 상태, 로딩, 오류, 성공, 권한 부족 같은 상태가 빠지지 않아야 합니다.
- 기능 카탈로그에는 코드에서 확인한 기능군, 진입점, 구현 상태, 관련 코드/문서, 미확인 사항이 있어야 합니다.
- 디자인 문서에는 디자인 방향, 레이아웃 원칙, 컴포넌트/상태, 반응형, 접근성, 구현 handoff 기준이 있어야 합니다.
- 기술 문서에는 시스템 구성, 데이터 흐름, 주요 선택지와 결정 이유, 되돌림 또는 변경 가능 지점이 있어야 합니다.
- QA 문서에는 핵심 사용자 흐름별 검수 항목, 경계 조건, 회귀 테스트 범위가 있어야 합니다.
- 의사결정/상태 문서에는 현재 결론, 결정 근거, 남은 이견, 다음 갱신 조건이 있어야 합니다.
- 운영/배포 문서에는 환경, 설정, 배포 절차, 롤백, 로그/모니터링, 장애 대응이 있어야 합니다.
- 온보딩/인수인계 문서에는 첫 진입 순서, 로컬 실행, 코드 맵, 흔한 작업, 주의할 위험 지점이 있어야 합니다.
- 사용자/서비스 문서에는 대상 사용자, 사용 절차, 빈번한 질문, 알려진 문제, 지원/에스컬레이션 기준이 있어야 합니다.
- 데이터/보안/정책 문서에는 수집/저장/보존/삭제, 접근권한, 민감정보, 감사 기준이 있어야 합니다.
- 성과/KPI 문서에는 지표 정의, 이벤트, 계산식, 수집 위치, 오해하기 쉬운 해석이 있어야 합니다.
- 문서가 현재 요청의 성공 기준을 직접 만족하는지, 불필요하게 범위가 커지지 않았는지 점검합니다.
- PDF 저장을 요청받은 경우, 한글과 Mermaid 렌더 품질을 위해 브라우저 기반 렌더를 우선 사용하고 실제 `.pdf` 파일 생성 여부까지 확인합니다.
- 문서가 기존 문서와 충돌하거나 중복되는 경우, 새 문서를 만들기보다 기존 문서를 갱신하고 연결을 정리합니다.
- 하네스 입력에서는 meeting report의 의견 원문을 복사하지 않고 합의, 이견, 사용자 확인 필요, 근거 링크로 압축했는지 확인합니다.

## 출력 규칙

- 아키텍처와 흐름 설명에는 Mermaid를 우선 사용합니다.
- API, payload, DB 엔티티, 필드 정의에는 표를 우선 사용합니다.
- 문서는 회사에서 실제 개발 착수, 구현, QA, 인수인계에 사용할 수 있는 밀도로 작성합니다. 제목만 많은 빈 문서나 일반론 문서는 만들지 않습니다.
- PDF 출력은 사용자가 요청했을 때만 수행하며, 기본 저장 위치는 원본 `.md`와 같은 폴더입니다.
- 문서 마지막에는 필요할 때 `관련 코드/문서`, `갱신 트리거`, `검증 방법` 섹션을 둡니다.
