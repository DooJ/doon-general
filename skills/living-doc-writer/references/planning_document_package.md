# 개발 착수 문서 패키지 기준
사용자가 "앱 만들자", "POC 만들자", "MVP 개발하자", "PRD 만들어줘", "개발 착수 문서 만들어줘", "요구사항/화면/API/일정/QA 문서 만들어줘"처럼 개발 실행을 전제로 요청하면 이 기준을 따른다.

## 기본 원칙
- 회의록 생성을 명시하지 않았다면 회의록은 만들지 않는다. 사용자 발화, 회의 요약, 아이디어/디자인 기획 문서를 입력 자료로 삼아 개발 착수 문서로 변환한다.
- 개발, 디자인, QA, 일정 관리의 독자와 갱신 주기가 달라질 때 문서를 분리한다. 요청 범위가 작고 한 문서에서 관리할 수 있으면 통합한다.
- 모든 문서는 `확정`, `가정`, `미정`, `사용자 확인 필요`를 구분한다.
- 실제 코드가 없는 초기 기획 단계에서는 코드 경로를 억지로 만들지 않는다. 대신 근거 자료와 추후 검증 방법을 남긴다.
- 문서 수의 하한은 두지 않는다. 아래 표는 선택 가능한 문서 세트이며, 요청의 성공 기준에 필요한 항목만 만들거나 기존 문서에 통합한다.
- 기존 문서의 경로와 식별자는 유지하고 정본·대체 관계를 manifest에 표시한다. 아래 경로를 맞추려고 동일 내용을 새로 복제하지 않는다.
- 서비스 전체 목표와 이번 개발 인도 범위를 분리한다. 후속 요구는 누락으로 두지 말고 이유·재검토 조건·초기 UI 처리까지 남긴다.
- 아이디어 자체나 디자인 방향이 아직 불명확하면 먼저 `idea_planning_package.md` 또는 `design_planning_package.md`로 돌아간다.

## 상황별 축소와 확장
- 백엔드가 없는 정적 웹, 개인 도구, 프로토타입은 `api-spec.md`를 제외하거나 `해당 없음` 사유를 manifest에 남긴다.
- UI가 없는 API/worker 프로젝트는 시각적 화면 대신 호출·이벤트·상태 전이 도식을 사용하고 스토리보드의 해당 없음 사유를 남긴다. 백엔드가 없는 UI는 API·DB를 발명하지 않고 로컬 상태/fixture 경계를 명시한다.
- 데이터 저장이 없는 도구는 `data-model.md`를 제외하거나 "로컬 상태만 사용"처럼 범위를 명시한다.
- 운영 절차, 배포, 장애 대응이 필요한 서비스는 `docs/operations/runbook.md`를 추가한다.
- 법무, 개인정보, 결제, 관리자 권한이 중요한 서비스는 `docs/project/policy-and-risk.md`를 추가한다.
- 기존 코드가 있는 프로젝트는 `feature-analyzer`로 확인한 사실을 각 문서의 근거로 연결한다.

## 생성 순서
1. `project-brief.md`로 목적, 사용자, 문제, 성공 기준을 먼저 고정한다.
2. `poc-plan.md`로 POC 필요 여부와 검증할 가장 위험한 가설을 정한다.
3. `mvp-scope.md`에서 MVP, 후속, 제외 범위를 정한다.
4. `prd.md`에서 제품 요구사항과 출시 판단 기준을 정하거나 `deferred` 사유를 남긴다.
5. `requirements.md`에서 기능 요구사항과 acceptance criteria를 QA 가능한 수준으로 쪼갠다.
6. `user-scenarios.md`와 화면 명세·시각적 스토리보드로 핵심 화면을 실제로 보고 흐름·상태·행동을 확인할 수 있게 한다.
7. `design-brief.md`로 화면 구현에 필요한 디자인 판단을 고정한다.
8. 기술 구성·데이터 모델을 실제 DB 물리 설계/migration과 API 상세 계약으로 연결한다. 화면에서 읽고 쓰는 값의 저장·계산·외부 출처를 확인한다.
9. WBS에 구현·연동·초기 데이터/계정 준비·검증·운영 인도 중 해당 작업을 배정하고 검수 ID와 연결한다. 최초 결과·정책·계정 생성이 뒤 단계에만 있어 앞 단계가 시작되지 못하는 의존 누락도 확인한다.
10. 아래 문서 간 연결 검토를 수행하고 고친 내용과 남은 결정/책임/차단 시점을 기록한다. `docs/README.md`에는 정본, 버전, 최종 확인일, 재생성 경로와 미검증 범위를 반영한다.

## 개발 착수 수준의 구체화

아래 항목은 해당 기능을 실제 구현할 때 필요한 최소 정보다. 작은 작업은 한 문서의 표로 통합할 수 있으며 엔진·웹 프레임워크·인증 제공자를 특정 프로젝트의 선택으로 고정하지 않는다.

### WBS
- 작업 행은 구현/검수가 가능한 산출물 단위로 나눈다. `작업 ID, 작업, 담당 역할/실명 상태, 선행 ID, 공수 범위/단위, 인도 단계, 연결 요구·행동·API·테이블/저장소·검수 ID, 산출물, 완료 기준, 상태`를 기록한다. UI/API/DB가 해당 없으면 이유를 적는다.
- 역할 담당과 실제 배정자를 구분하고 미배정/미정 날짜를 드러낸다. 공수의 단위·가정·조건부 작업을 표시하며 총 인일을 달력 납기로 바꾸지 않는다. 가용 인력과 선행 관계 확인 후 시작/종료일을 정한다.
- 외부 연동, 인증/권한, migration/초기화, 실패 복구, 필요한 보존/삭제, QA·배포를 기능 화면 밖의 작업으로도 점검한다. 문서·fixture 통과를 기능 구현 완료로 바꾸지 않는다.
- 선행 ID 실재·순환 없음, 포함 API/행동의 작업 배정, 조건부 작업의 발동 조건·차단 시점을 확인한다. 가져갈 작업 도구가 있으면 표/CSV/구조형 파일 중 적합한 형식으로 제공하고 정본을 하나로 둔다.

### DB 물리 설계
- 저장 엔진/버전/필수 확장과 논리 모델→실제 테이블·컬렉션·키 대응을 정한다. 관계형이면 타입·길이·NULL/default·PK/FK/unique/check·인덱스와 삭제 동작을 명시한다. 비관계형이면 그에 맞는 문서 구조·파티션/키·인덱스·일관성 제약을 명시한다.
- 생성/변경/삭제, 중복·동시 갱신, 작업 예약·멱등 응답 같은 원자성 경계를 정의한다. 권한 격리, 상태 전이, 이력·버전·게시 기준, 날짜/시간대·좌표는 해당 도메인에서 필요한 경우 물리 설계로 연결한다.
- 실행 가능한 migration/DDL 또는 엔진에 맞는 초기화 정의와 컬럼/필드 사전을 제공한다. 정본은 migration/스키마로 정하고 사전·ERD·예제의 생성/검증 경로를 남긴다. API 출력은 저장·계산·외부 조회 중 출처를 표시한다.
- 적용 순서·확장 의존·기존 자료 backfill·변경 호환·복구/전진 수정 방법을 정한다. 빈 DB와 변경 대상 기준 버전 중 실제 인도에 필요한 적용 경로를 검증한다. 불가능한 rollback을 가능하다고 쓰지 않는다.
- 격리된 시험 DB에서 적용·대표 제약·중복/권한/동시성 경계를 위험에 맞게 검증한다. 논리 FK나 정적 구문 확인만으로 실행 통과를 주장하지 않는다. 외부 확장/공간 실행 등 못 한 검증은 별도 미완료로 남긴다. 운영 DB를 문서 검증 대상으로 임의 변경하지 않는다.
- 삭제/가용성 정책은 원본뿐 아니라 이벤트 payload, outbox, 파생 인용, 캐시, 작업 payload, 파일·백업 중 실제 복제 경로까지 추적한다. 감사·중복 방지 메타데이터와 삭제할 본문을 구분하고 복원/재전송으로 삭제 내용이 되살아나는 경계를 검수한다.

### 시각적 스토리보드
- UI가 있으면 실제 화면 또는 와이어프레임을 열어 볼 수 있는 산출물(HTML, 디자인 프레임, 주석 이미지 등)을 포함한다. 텍스트 화면 목록이나 API 표만으로 시각적 스토리보드 완료를 대신하지 않는다. PDF는 요청 시 제공한다.
- 화면 ID·영역 번호·행동 ID를 고정하고 시각 영역과 주석을 연결한다. 행동마다 입력/검증→요청/처리→결과/전환→예외/복구, 기능·대상 범위, 관련 API/데이터/검수 ID를 확인할 수 있게 한다.
- 초기/로딩/빈/성공/오류/권한 부족과 필요한 부분·유보·오래됨·만료 상태를 표시한다. 비동기 수락과 실제 완료, 폴링·재시도·중복 클릭·닫기/뒤로 가기의 보존/초점 복귀는 해당 동작에서 구체화한다.
- 관리/운영 등 사용자 목적과 권한이 다르면 화면군을 구분하고 같은 기능을 재사용하는 경우 범위 차이를 보여준다. 시안의 가상 수치·로컬 동작과 실제 API 연동 상태를 구분한다.
- 후속 기능은 초기 화면에서 숨김/비활성/안내 중 선택한 처리와 사유를 명시하고 없는 endpoint나 성공을 가장하지 않는다. 실제 렌더·번호 대응·주요 이동을 확인하며 디자인 시안 검증을 서버 구현 검증으로 표시하지 않는다.

### 문서 간 연결 검토
- `요구 ID → 초기 범위/단계 → 화면·행동/시스템 흐름 ID → API operationId/이벤트 → 테이블·저장소 또는 계산 출처 → WBS ID → 검수 ID`로 추적한다. 해당 없음은 사유, 후속은 제외 이유·재검토 조건·초기 UI 처리를 남긴다.
- 화면이 아닌 **행동 단위**로 읽기·쓰기·상세·옵션·원문/첨부·승인·현재 버전·재시도/되돌림 경로를 대조한다. 화면 밖의 이벤트/배치/운영 작업은 별도 흐름 ID로 포함한다.
- 연결 ID가 존재하는지만 검사하지 않는다. 필수/선택/null, enum·상태 이름·전이, 권한/위임·대상 범위, 경로/메서드·응답 코드, 페이지/cursor·정렬·필터, 단위/날짜, 버전/스냅샷, 비동기 작업 ID, 멱등성·오류/삭제 의미가 서로 일치하는지 확인한다.
- 예: 운영 기준 팝업이 관리자 전용 API를 요구하는지, 승인이 즉시 게시로 오인되는지, 되돌림이 새 안전 결과인지 과거 포인터 복원인지, 재시도가 새 작업인지 같은 작업의 새 시도인지 명세에서 하나로 정한다. 도메인에 없는 승인/게시 기능을 새로 추가하라는 뜻은 아니다.
- 포함 행동·API에 담당 작업/검수 누락0, 존재하지 않는 ID 참조0, 선행 순환0을 목표로 전수 대조한다. 포함/부분/후속/해당 없음과 검증됨/미검증을 분리하고 충돌은 정본과 소비 문서를 함께 수정한다. 큰 표는 CSV/JSON으로 보조 검증할 수 있다.
- 가능한 검증은 계약 스키마와 정상/오류 예제, DDL 적용·제약, 참조/로컬 링크, WBS 선행 DAG, 시각 산출물 렌더다. 의미·인가·동시성·E2E 중 미구현 항목은 테스트 계획/차단 조건으로 남긴다. 확인할 수 없는 비율·건수·합격을 만들지 않는다.

## 완료 기준
- 문서 세트가 POC, MVP, PRD, 요구사항, 화면, 디자인, 기술, 일정, QA를 모두 다룬다.
- 요구사항과 화면 문서에 "정상 흐름"뿐 아니라 오류, 빈 상태, 권한, 예외가 포함되어 있다.
- 디자인 문서가 단순 분위기 설명이 아니라 구현 가능한 레이아웃, 컴포넌트, 상태, 반응형 기준을 포함한다.
- 기술 문서가 선택한 구조와 선택하지 않은 대안, 변경 가능 지점을 설명한다.
- QA 문서가 요구사항과 화면 흐름을 검증할 수 있는 체크리스트로 연결된다.

- 포함된 행동·시스템 흐름에 구현/저장·검수 연결이 있고 후속·해당 없음의 이유가 남아 있다. WBS·DB·API·스토리보드의 상태/권한/필드/식별자가 충돌하지 않는다.
- 실제 실행한 계약·DDL·렌더/연결 검증의 명령·환경·결과와 미검증 범위를 남긴다. 문서 준비, 계약 검증, 제품 구현, 사용자 공개 승인을 구분한다.
