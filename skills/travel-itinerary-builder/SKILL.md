# 여행 일정 합성 및 검증

## 역할과 발동 경계

사용자가 "이 예약 정보로 최종 일정 짜줘", "조사한 후보를 3박 4일로 묶어줘", "비용과 플랜 B까지 정리"처럼 여러 정보를 하나의 실행 계획으로 합치려 할 때 사용합니다. `travel-planner`에서는 마지막 합성 단계입니다.

이 스킬은 새 항공편·숙소·장소를 폭넓게 검색하는 역할이 아닙니다. 필수 입력이 부족하면 관련 조사 스킬을 요청하거나 현재 결과를 `partial`로 표시합니다. 후보만 있는 항목을 예약 완료로 승격하지 않습니다.

## 입력

- 정규화된 여행 컨텍스트와 `context_revision`
- 사용자 제공 확정 예약과 비용
- `travel-flight-search` 결과 또는 확정 장거리 이동
- `travel-lodging-search` 결과 또는 확정 숙소
- `travel-destination-research`의 날씨·현지 정보
- `travel-place-search`의 선택·후보 장소
- `travel-transport-search`의 구간별 이동 결과
- 사용자가 정한 여행 목적, 체력, 식이, 예산, 이동 제약

모든 입력은 가능하면 `input_revision`, `as_of`, `evidence`, `status`, `freshness`를 유지합니다. 현재 `context_revision`과 다른 결과는 `freshness: stale`로 취급하고 자동 합성하지 않습니다.

## 합성 절차

### 1. 상태 정규화

모든 예약·장소·교통을 `unknown`, `assumed`, `candidate`, `selected`, `booked` 중 하나로 정리합니다. 일정표에는 최소한 `candidate`, `selected`, `booked`를 명시해 후보와 확정 예약을 구분합니다.

### 2. 고정점 배치

항공·열차·배의 출도착, 숙소 체크인·체크아웃, 예약 식당·투어처럼 시간이 고정된 `booked` 항목을 먼저 놓습니다. 이후 날씨, 영업시간, 식사 시간, 체력을 고려해 `selected` 항목을 배치합니다.

### 3. 마스터 위치 체인

전체 여행을 다음 체인으로 연결합니다.

```text
집/출발지 -> 출국 거점 -> 장거리 이동 -> 도착 거점
-> 숙소/첫 방문지 -> 날짜별 방문지 -> 숙소
-> 출국 거점 -> 장거리 이동 -> 집/귀착지
```

각 행은 날짜, 시작 위치, 종료 위치, 활동·이동, 소요, 버퍼, 예약 상태, 비용을 갖습니다. 앞 행의 종료 위치와 다음 행의 시작 위치가 이어지는 위치 연속성을 확인합니다.

### 4. 카테고리별 요약

일정표를 쓰기 전에 장거리 이동, 숙소, 관광지·체험, 식당·카페를 한곳에 다시 모읍니다. 각 카테고리에는 `booked`·`selected`·`candidate` 상태, 핵심 선택 이유, 비용·시간의 기준 시각, 어느 날짜 일정에 반영됐는지를 표시합니다. 조사 결과를 따로 나열한 채 합성을 끝내지 않습니다.

### 5. 일자별 메인 일정표

- 첫날: 집 출발, 공항 접근, 탑승 수속, 출국, 입국, 수하물, 숙소 또는 첫 장소까지 포함합니다.
- 체류일: 숙소에서 시작하고 원칙적으로 숙소로 돌아옵니다.
- 숙소 이동일: 체크아웃, 짐 보관·배송, 도시 간 이동, 다음 체크인을 먼저 배치합니다.
- 마지막 날: 체크아웃, 짐, 공항·역 이동, 탑승, 입국, 귀가까지 포함합니다.
- 하루 핵심 장소는 기본 2~3개로 제한하고 식당·카페는 실제 동선 안의 선택지로 둡니다.
- 날짜별 내용을 단순 리스트로 쓰지 않고 `시간`, `시작`, `종료`, `이동·활동`, `소요·버퍼`, `예상 비용`, `예약·상태`, `메모` 열을 가진 Markdown 표로 작성합니다.
- 사용자가 실제로 따를 **메인 일정**을 먼저 완성합니다. 날씨·대기·휴무·교통 장애에 따른 차선책과 전환 조건은 메인 일정과 분리한 짧은 변경 대응표에 둡니다.
- 차선책은 같은 권역·비슷한 소요시간을 우선하며, 전환 시 추가 이동 시간, 비용 차이, 예약 취소·재확인 영향을 적습니다. 일정 전체를 다시 쓰기보다 `1일차↔2일차 교환`, `한 장소 제외`, `인근 실내 장소 대체`처럼 실행 가능한 최소 변경으로 제시합니다.
- 항공·예약 투어처럼 고정된 `booked` 항목은 임의 교체안을 만들지 않고 지연·결항·휴무 상황의 비상 대안과 전환 조건을 적습니다.
- 예약된 고정점에 즉시 대응해야 하는 비상 조치만 해당 행의 메모에 짧게 적을 수 있습니다.
- 사용자가 후보 번호나 장소를 고르면 상태를 갱신하고 영향받는 이후 행만 다시 계산합니다.

### 6. 비용 장부

비용을 확정, 예상, 선택, 변동, 비상 예산으로 나눕니다. 각 항목에 통화, 금액, 수량, `1인`·`객실`·그룹·차량 등 기준, 세금·봉사료·입장료 포함 여부, 계산식을 둡니다. 통화별 소계와 환산 기준일을 표시하고 항목 합계와 총계가 일치하는지 검산합니다.

### 7. 날씨·휴무·지연 변경안

우천·폭염·휴무·매진·교통 지연별 플랜 B를 둡니다. 대체 장소만 나열하지 않고 시간, 비용, 예약, 이동 영향과 전환 판단 시점을 적습니다.

예보가 아직 열리지 않은 날짜는 최근 여러 해의 평년·과거 관측을 `예측`으로 표시하고, D-10·D-3·출발 전날에 최신 예보로 갱신할 항목을 남깁니다. 실제 예보가 나온 뒤에는 비·눈·강풍·한파·폭염 조건에 따라 날짜 교환 또는 일부 장소 대체 여부를 결정합니다.

### 8. 준비물과 실행 정보

국내외 여행 모두 다음을 일정과 계절에 맞게 합성합니다.

- 준비물: 신분증·승차권·예약 확인, 기온·강수·바람에 맞는 의류와 신발, 충전기·보조배터리·통신 수단, 상비약·위생용품, 짐·쇼핑·음식 포장 용품
- 예약·탑승: 예매 오픈 시점, 취소·변경 조건, 출발지 도착 권장 시각, 승강장·터미널 확인 방법
- 이동·짐: 현지 교통 결제 수단, 막차·배차 주의, 체크인 전·체크아웃 후 짐 보관과 실패 시 대안
- 운영·결제: 휴무·라스트오더·예약 필요 여부, 카드·현금·간편결제 범위
- 안전·비상: 기상 악화 시 행동, 야간 이동 주의, 의료·경찰·긴급 연락 정보

국내 여행이면 112·119와 해당 지역의 교통·시설 운영 정보를 포함합니다. 해외 여행이면 여기에 입국, 여권·비자, 로밍·통신, 환전·해외 결제, 대사관·현지 긴급 전화, 필요한 최소 현지 표현을 추가합니다. 국내 여행이라는 이유로 준비물과 실행 정보를 생략하지 않습니다.

## 완료 전 일관성 게이트

다음을 모두 통과하기 전에는 결과를 `complete`로 표시하지 않습니다.

1. 후보·선택·예약 상태: `candidate`, `selected`, `booked`가 섞이지 않았는가
2. 달력: 날짜·요일·공휴일과 장소의 영업시간·휴무가 일치하는가
3. 동선: 모든 구간의 위치 연속성이 있고 순간 이동이나 불필요한 왕복이 없는가
4. 장거리 이동: 공항 접근, 탑승 수속, 입출국, 수하물, 환승, 체크인 버퍼가 있는가
5. 교통: 추천 수단이 해당 날짜의 실제 운행 시간·막차와 맞고 지연 대안이 있는가
6. 짐: 체크인 전·체크아웃 후·숙소 이동일의 짐 처리가 있는가
7. 비용: 비용 장부의 항목 수·수량·소계·총계가 맞고 1인·객실·그룹 기준이 명시됐는가
8. 부대 비용: 세금, 봉사료, 입장료, 수하물, 보증금 포함 여부가 표시됐는가
9. 날씨: 예보와 평년 자료를 구분했고 우천·폭염·악천후 대체안이 있는가
10. 합성: 장거리 이동·숙소·관광지·식당 카테고리 요약이 있고 각 항목이 날짜별 일정과 연결됐는가
11. 표현 밀도: 메인 일정이 중심에 있고 날씨·휴무·지연 변경안은 별도 보조표로 분리됐는가
12. 준비·실행 정보: 국내외 해당 범위의 준비물, 예약·탑승·짐·결제·현지 이동·안전·비상 정보가 있는가
13. 최신성: 변동 정보마다 근거와 기준 시각 `as_of`가 있고, 미래 예보 갱신 시점이 있는가
14. 접근성: 동행자의 체력·연령·장애·식이 제약이 이동과 장소 선택에 반영됐는가
15. 도메인 커버리지: 전체 여행 요청의 항공·장거리 이동, 숙소, 목적지 정보, 장소, 현지 교통, 일정 합성이 모두 `ready`, `confirmed_input`, `user_excluded` 중 하나인가

## 부분·차단 결과 처리

- 필수 도메인이 `partial`이면 일정도 `partial`입니다. 사용 가능한 초안과 누락 영향, 다음 확인 시점을 함께 제공합니다.
- 필수 도메인이 `blocked`이면 해당 도메인에 의존하는 일정을 확정하지 않고 해소 방법을 제시합니다.
- 미요청 선택 영역이 `skipped`인 것은 완료를 막지 않지만, 일정 안전에 필수인 교통·숙소·장거리 이동은 생략할 수 없습니다.
- `freshness: stale` 입력은 재검증 전까지 후보 배치의 근거로만 보고 확정 비용·시간에 합산하지 않습니다.
- 일부 조사 실패를 임의의 값으로 메우거나 `complete`로 표시하지 않습니다.
- 도메인 커버리지 행을 만들지 않거나 필수 도메인을 조용히 생략한 결과는 관광 일정이 자세해도 `complete`가 아닙니다.

## 산출물

사용자용 출력은 항상 Markdown으로 작성합니다. Markdown이 canonical 원본이며 표, 체크박스, 상태 라벨과 링크도 Markdown 문법을 사용합니다. HTML은 사용자가 명시적으로 요청한 경우에만 Markdown에서 파생하는 보조 산출물이며 Markdown 결과를 대체하지 않습니다.

1. 기준 조회일, `context_revision`, 여행 단계, 확정·후보·확인 필요 요약
2. 장거리 이동·숙소·관광지·식당별 확정·후보 요약과 일정 반영일
3. 핵심 선택 이유와 예약 우선순위
4. 마스터 여정 체인
5. 날짜별 메인 일정표
6. 이동 및 짐 처리 요약
7. 통화·기준이 명확한 비용 장부
8. 날씨·휴무·지연 변경 대응표와 전환 조건
9. 출발 전 준비물 체크리스트
10. 예약·탑승·짐·결제·현지 이동·안전·비상 연락 등 국내외 해당 범위의 실행 정보
11. 근거와 기준 시각, 예보 갱신 시점, 미해결 질문

사용자가 채팅만 원하면 파일을 만들지 않습니다. 파일을 원하면 `travel-planner`의 기존 Markdown·HTML 저장 규칙과 시각화 reference를 재사용합니다.

## 완료 조건

- 모든 필수 입력이 현재 `context_revision`과 일치합니다.
- 고정 예약과 후보가 구분되고 전체 위치·시간 체인이 끊기지 않습니다.
- 비용 합계, 기준, 포함 여부가 검산됐습니다.
- 메인 일정과 변경안이 분리되어 있고, 날씨·휴무·지연 대체안과 국내외 해당 범위의 준비물·실전 정보가 있습니다.
- 필수 도메인 `status`에 `partial`·`blocked`가 없고 `freshness: stale`도 없을 때만 `complete`입니다.
- 예약·결제·로그인·개인정보 입력은 수행하지 않습니다.
