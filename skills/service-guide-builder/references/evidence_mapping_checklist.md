# 화면 요소와 기능의 근거 연결

화면을 찾은 뒤 설명 버튼을 만들기 전에 사용한다. **화면 → 해당 상태에서 보이는 요소 → 핸들러/조건 → 사용자에게 보이는 결과**를 한 줄로 추적한다. 설명을 먼저 쓰고 나중에 비슷한 버튼에 붙이지 않는다.

## 조작 요소 목록

| 화면·상태 ID | 요소 ID와 실제 문구 | 위치·가시 조건 | UI 근거 | 동작 근거 | 결과·다음 화면 | 판정 |
|---|---|---|---|---|---|---|
| 예: settings-account/default | save-profile · 저장 | 편집 모드에서만 표시 | 컴포넌트·문자열 경로 | 클릭 핸들러·검증 경로 | 성공 메시지 또는 입력 오류 | 확인됨/일부 확인/미확인 |

- 버튼·메뉴·탭·입력·선택 가능한 카드 등 사용자의 주요 조작을 화면에서 찾는다. 같은 이름이라도 화면·상태가 다르면 별도 행으로 둔다.
- UI 코드의 표시 조건과 문자열을 확인하고, 런타임 또는 캡처에서 실제 표시를 대조한다.
- 이벤트 핸들러, 연결된 ViewModel/상태, 라우트, API·저장 동작을 필요한 깊이까지 따라간다. 호출이 있다는 사실과 성공 결과가 실제로 보인다는 사실을 구분한다.
- 연결되지 않은 버튼, 권한 때문에 비활성인 버튼, mock 데이터는 있는 그대로 표시한다. 기능을 추정해 설명하지 않는다.
- 비조작 영역을 설명할 수는 있지만 실제 버튼인 것처럼 표현하지 않는다.

## 가이드 데이터의 최소 계약

설명 포인트는 `screen_id`, `state_id`, `target_id`, 사용자에게 보이는 이름, 조작 조건, 동작, 결과, 근거 경로/심볼, 확인 수준을 갖는다. 대상 요소에도 같은 `screen_id`·`state_id`·`target_id`를 연결한다. 구현 기술에 따라 식별자 이름은 바꿀 수 있지만 **현재 중앙 화면·상태의 실제 요소 하나와 설명 하나가 정확히 대응**해야 한다.

가이드가 만들어진 뒤 다음을 검사한다.

1. 설명 데이터의 대상 ID가 현재 화면·상태에서 정확히 한 번 존재하는가?
2. 요청한 주요 조작 중 설명 없이 남은 요소와 근거 없이 설명만 있는 요소는 무엇인가?
3. 화면 전환·언어·권한·상태 변경 뒤 이전 화면의 요소가 선택되거나 설명되는가?
4. 설명 속 동작과 실제 핸들러의 조건·결과가 일치하는가?

기술적으로 가능한 경우 대상 ID의 누락·중복 검사를 자동화한다. 불일치한 항목은 숨기지 말고 수정하거나 미확인으로 표시한다. 완료 보고에는 요청된 핵심 화면·조작의 수와 검증된 수를 남긴다.

## 근거 충돌

실행 화면·코드·오래된 캡처가 다르면 현재 배포 버전과 확인 날짜를 먼저 맞춘다. 최신 화면의 시각적 배치는 실행 캡처를, 기능의 조건과 데이터 흐름은 실제 실행 결과 및 코드를 우선한다. 서로 다른 버전의 근거를 조합해 하나의 화면처럼 만들지 않는다.
