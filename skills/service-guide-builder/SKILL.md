# Service Guide Builder

## 목적

기존 서비스나 앱의 실제 화면을 기반으로, 사용자가 화면을 클릭하면서 기능 설명을 확인할 수 있는 인터랙티브 웹 가이드를 만든다.

가이드는 예쁜 설명 페이지가 아니라 실제 제품 화면을 이해하기 쉽게 재현한 문서여야 한다. 코드, 레이아웃, 문자열 리소스, 캡쳐 이미지, 런타임 동작으로 확인되지 않은 화면이나 기능을 임의로 만들지 않는다.

정적 사용 설명서, FAQ, 운영 매뉴얼을 요청한 경우에는 이 스킬을 호출하지 않고 `living-doc-writer`로 라우팅한다. 화면별 설명 요청만으로 인터랙티브 웹페이지 제작을 가정하지 않는다.

## 보조 자료

작업 범위가 넓거나 산출물 구조를 잡아야 할 때는 필요한 파일만 추가로 읽는다.

- 출력 위치와 파일 구성을 정할 때: `references/guide_output_patterns.md`
- 클릭 영역, 강조 박스, 이전/다음 흐름을 만들 때: `references/hotspot_interaction_patterns.md`
- 실제 코드와 설명 포인트의 근거를 연결할 때: `references/evidence_mapping_checklist.md`
- 상태 화면 누락을 점검할 때: `references/state_matrix_checklist.md`
- 가이드 폴더 README를 만들 때: `templates/guide_readme_template.md`
- 최소 구현 예시가 필요할 때: `examples/click-guide-sample/index.html`

## 기본 원칙

- 실제 코드와 화면을 먼저 확인한다.
- UI 레이아웃, 버튼명, 색상, 상태값, 문구는 실제 제품을 기준으로 한다.
- 없는 기능을 있는 것처럼 설명하지 않는다.
- 가이드에서 표현한 화면이 실제 앱 변경을 의미한다면 사용자에게 먼저 구분해서 알린다.
- 고정 설명 패널이 있으면 마우스 오버보다 클릭 방식을 우선한다.
- 화면 비율, 가로/세로 전환, 언어, 강조 표시, 팝업, 오류 메시지를 실제 동작 기준으로 맞춘다.
- 정적 HTML 가이드, 앱 내부 `/guide` 라우트, 이동용 엔트리 페이지 중 어떤 산출물인지 먼저 구분한다.
- 가이드 탐색 단위는 화면 단위, 기능 단위, 혼합형 중에서 먼저 판단하고 작업한다.
- 분할 방식, 포함 범위, 표현 방식이 복잡해지거나 사용자 의도와 달라질 수 있으면 실제 구현 전에 사용자 확인을 받는다.
- 독립 가이드 폴더에는 범위, 근거, 갱신 트리거, 검증 방법을 담은 README를 함께 둔다.
- 아직 구현되지 않은 기능을 보여줘야 한다면 `mock`, `예정`, `미연결` 상태로 명확히 표시한다.
- 변경 후에는 브라우저에서 실제 렌더링을 확인한다.

## 작업 절차

### 1. 분할 방식 판단

가이드를 만들기 전에 탐색 기준을 화면 단위, 기능 단위, 혼합형 중 하나로 정한다. 사용자가 명시한 기준이 있으면 그 기준을 우선한다.

화면 단위가 적합한 경우:

- 사용자가 "화면별 가이드", "각 화면 설명", "페이지별 사용법"처럼 화면 구조를 기준으로 요청한 경우
- 사용자가 실제 화면을 보며 버튼, 영역, 상태를 익히는 것이 목적인 경우
- 화면별 UI 차이, 권한별 화면, 가로/세로 화면, 팝업과 오류 상태를 비교해야 하는 경우
- 가이드 대상이 장비 화면, 키오스크, 앱 화면처럼 시각적 위치와 조작 순서가 중요한 경우

기능 단위가 적합한 경우:

- 사용자가 "로그인 방법", "결제 흐름", "파일 업로드", "설정 변경"처럼 수행 과업을 기준으로 요청한 경우
- 하나의 기능이 여러 화면, 팝업, 상태, 권한을 가로질러 이어지는 경우
- 운영자 교육, QA 시나리오, 고객지원 응대처럼 사용자의 목적 달성 흐름이 중요한 경우
- 같은 화면 안에 서로 독립적인 기능 묶음이 많아 화면 단위로 나누면 설명이 흩어지는 경우

혼합형이 적합한 경우:

- 좌측 탐색은 화면 단위로 두고, 우측 설명 패널이나 하위 탭은 기능 단위로 묶는 것이 이해하기 쉬운 경우
- 핵심 사용 흐름은 기능 단위지만, 각 단계의 실제 UI 위치 확인이 필요한 경우
- 화면과 기능이 모두 중요한 관리자 콘솔, 장비 운영 도구, 복합 대시보드인 경우

다음 조건에서는 바로 만들지 말고 먼저 확인한다.

- 화면 단위와 기능 단위가 모두 가능하고 어느 쪽이 더 중요한지 실제 근거만으로 판단하기 어려운 경우
- 사용 대상이 운영자, 최종 사용자, 개발자, QA 중 누구인지에 따라 분할 방식이 달라지는 경우
- 사용자가 요청한 산출물이 교육 자료인지, 고객지원용 가이드인지, 제품 내 도움말인지 불명확한 경우
- 기존 문서, 메뉴 구조, 릴리즈 범위와 충돌할 수 있는 분류 체계를 새로 만들어야 하는 경우
- 포함할 화면이나 기능 목록을 에이전트가 임의로 정해야 하는 경우
- 혼합형 구조가 필요하거나, 화면/기능 흐름이 많아 사용자가 기대한 가이드보다 복잡해질 수 있는 경우

질문은 길게 하지 않는다. 예: "이번 가이드는 화면별 탐색이 좋을까요, 기능별 수행 흐름이 좋을까요? 판단이 애매하면 화면 목록을 먼저 보여드리고 혼합형으로 진행하겠습니다."

판단 후에는 작업 시작 메시지나 README에 선택한 분할 방식과 이유를 한 줄로 남긴다.

### 2. 작업 전 확인 게이트

가이드 구현을 시작하기 전에 다음 내용을 짧게 제안하고 사용자 확인을 받는다. 사용자가 이미 분할 방식, 포함 범위, 산출물 형태를 명확히 지정했고 단일 화면이나 단일 기능처럼 단순한 경우에는 바로 진행할 수 있다. 작업 중 실제 구조가 예상보다 복잡해지거나 사용자 의도와 달라질 가능성이 생기면 멈추고 다시 확인한다.

- 제안 분할 방식: 화면 단위, 기능 단위, 혼합형 중 하나
- 선택 이유: 실제 화면 구조, 기능 흐름, 사용 목적 기준
- 포함할 화면 또는 기능 목록
- 화면 단위/기능 단위별 표현 방식
- 산출물 위치와 형태
- 확인이 필요한 애매한 결정

확인 질문 예:

- "이 가이드는 화면 단위로 실제 화면을 거의 동일하게 재현하고, 각 컴포넌트를 클릭해 설명하는 방식으로 진행해도 될까요?"
- "이 기능은 여러 화면을 거치므로, 먼저 기능 위치를 보여준 뒤 해당 기능 영역을 확대해 설명하는 기능 단위 가이드로 진행해도 될까요?"
- "화면 탐색과 기능 흐름이 모두 중요해 보여 혼합형으로 제안합니다. 이 구조로 진행할까요?"

### 3. 범위 확인

다음을 먼저 정리한다.

- 가이드 대상 서비스 또는 앱
- 선택한 분할 방식: 화면 단위, 기능 단위, 혼합형 중 하나
- 화면 카테고리 순서
- 포함할 화면 목록
- 포함할 기능 흐름 목록
- 팝업, 로딩, 오류, 빈 상태, 보기/수정 모드 같은 상태 화면
- 지원 언어
- 실제 화면 비율과 방향
- 산출물 형태: 정적 `guide/index.html`, 문서형 `docs/*-guide/index.html`, 앱 내부 `/guide`, 이동용 엔트리 페이지 중 무엇인지
- 가이드 README가 필요한 위치와 실행 방법

### 4. 실제 근거 수집

다음 파일과 자료를 확인한다.

- Android XML, Compose, SwiftUI, JSX/TSX, HTML 같은 UI 레이아웃
- `strings.xml`, i18n JSON, locale 파일 같은 문자열 리소스
- Activity, Fragment, ViewModel, Controller, Repository 같은 동작 코드
- 앱 아이콘, 로고, 이미지, 폰트
- 실제 캡쳐 이미지나 장비 화면
- 구현된 기능과 아직 mock/예정/미연결인 기능의 경계

화면은 캡쳐를 기준으로 보고, 동작은 코드를 기준으로 판단한다.

### 5. 가이드 구조 설계

기본 구조는 다음을 우선한다.

- 좌측: 화면 목록과 카테고리
- 중앙: 실제 화면처럼 보이는 화면 재현 영역
- 우측: 선택한 버튼이나 영역의 상세 설명
- 상단: 해상도, 방향, 언어, 강조 표시, 이전/다음 버튼
- 필요 시 하단: 오류, 메시지, 상태 목록

화면 요소와 설명은 가능하면 `data-guide-target` 같은 안정적인 식별자로 연결한다. 고정 좌표만으로 설명을 붙이면 실제 화면 구조가 바뀔 때 깨지기 쉽다.

분할 방식별 구조:

- 화면 단위: 실제 화면을 중심에 크게 재현하고, 각 기능이나 컴포넌트를 클릭하면 설명 패널이 바뀌게 만든다.
- 기능 단위: 먼저 해당 기능이 실제 제품의 어느 화면과 위치에 있는지 보여주고, 이어서 해당 기능 영역만 확대해 세부 설명을 제공한다.
- 혼합형: 화면 목록을 기본 탐색으로 두되, 주요 사용 흐름은 기능 단위 확대 설명으로 연결한다.

### 6. 화면 재현

실제 화면을 먼저 재현한다.

- 레이아웃 구조를 실제 UI 파일에서 가져온다.
- 실제 문자열 리소스를 사용한다.
- `visible/gone`, 선택 상태, 토글 상태를 반영한다.
- 버튼 색상, 배경색, 여백, 글자 크기를 실제 화면과 맞춘다.
- 16:9, 9:16 같은 실제 화면 비율을 유지한다.
- 고정 장비 화면 안에 불필요한 스크롤이 생기지 않게 한다.
- 실제 해상도 때문에 글자가 너무 작으면 돋보기나 확대 패널을 사용한다.
- 구조화된 UI 리소스(Android XML, strings, i18n JSON 등)는 가능하면 변환/추출 스크립트로 재현 정확도를 높인다.

화면 단위 가이드는 다음 기준을 따른다.

- 해당 화면을 실제 화면과 99% 수준으로 동일하게 재현하는 것을 목표로 한다.
- 캡쳐, UI 코드, 문자열 리소스, 실제 런타임 화면을 기준으로 크기, 색상, 여백, 정렬, 문구, 상태를 맞춘다.
- 불가피하게 실제 화면과 달라지는 부분은 README나 설명 패널에 이유를 남긴다.
- 화면 안의 버튼, 입력창, 목록, 탭, 토글, 상태 배지 같은 기능 또는 컴포넌트 단위로 클릭 설명을 붙인다.
- 설명 패널이 실제 화면 재현을 가리지 않도록 배치한다.

기능 단위 가이드는 다음 기준을 따른다.

- 첫 화면에서는 해당 기능이 실제 제품의 어느 화면, 메뉴, 영역에 있는지 먼저 보여준다.
- 위치 설명 화면은 실제 화면 전체 맥락을 유지하고, 기능 영역을 강조 표시한다.
- 다음 단계에서는 해당 기능 영역만 더 크게 표현해 세부 요소, 상태, 입력값, 결과를 설명한다.
- 확대 표현은 실제 UI를 왜곡하지 않고, 크기만 키워 읽기 쉽게 만든다.
- 기능이 여러 화면을 거치면 각 단계마다 "전체 위치 확인 화면"과 "기능 확대 설명"을 연결한다.

### 7. 설명 작성

각 클릭 영역에는 다음 정보를 필요한 만큼 작성한다.

- 기능 이름
- 사용자가 보는 내용
- 클릭하거나 선택했을 때의 동작
- 결과 상태
- 사용 조건이나 주의점
- 근거 코드 또는 리소스 위치

설명은 운영자가 이해할 수 있는 말로 쓴다. `Trigger / Action / Result` 같은 추상 표현은 사용자가 원할 때만 쓴다.

근거는 가능하면 화면 단위가 아니라 클릭 영역 단위로 연결한다. 각 설명 포인트에는 관련 UI 파일, 동작 코드, 문자열 리소스, mock 데이터 위치 중 확인한 것을 남긴다.

### 8. 언어 처리

제품이 다국어를 지원하면 가이드도 같은 언어를 지원한다.

- 실제 앱의 언어 목록을 따른다.
- 화면 문구는 문자열 리소스 기준으로 넣는다.
- 기능 제목과 설명도 언어별로 제공한다.
- 언어 전환 시 화면 문구와 설명 패널이 함께 바뀌는지 확인한다.

### 9. 상태 화면 처리

다음 상태는 별도 화면 또는 선택 가능한 상태로 표현한다.

- 로딩 단계
- 수동 연결 팝업
- 네트워크 오류
- 상태 메시지
- 토스트 또는 다이얼로그
- 파일 목록 타입
- 보기/수정 모드
- 토글 모드
- 가로/세로 화면
- 데스크톱/모바일/태블릿 변형
- 권한 없음, 데이터 없음, 일부 실패, 부분 완료, 미연결 외부 서비스

특정 모드에서만 나오는 화면은 해당 모드임을 설명에 명확히 표시한다.

## 금지 사항

- 실제 코드에 없는 버튼이나 화면을 임의로 만들지 않는다.
- 캡쳐와 다르게 생긴 화면을 실제 화면처럼 설명하지 않는다.
- 가이드 편의를 위해 실제 앱 동작을 왜곡하지 않는다.
- 설명 화면 때문에 실제 화면 재현을 가리지 않는다.
- 클릭 강조색이 배경과 섞여 안 보이는 상태로 두지 않는다.
- 실제 화면을 로드하지 않았는데 실제 페이지를 임베드한 것처럼 설명하지 않는다.
- 확인하지 않은 기능을 추측해서 문서화하지 않는다.

## 검증 기준

완료 전 다음을 확인한다.

- 좌측 메뉴 순서가 사용자 요청과 맞는가
- 화면 이름과 버튼 문구가 실제 리소스와 맞는가
- 화면 단위 가이드가 실제 화면과 99% 수준으로 동일하게 보이도록 재현되었는가
- 기능 단위 가이드가 기능 위치 확인 화면과 기능 확대 설명 화면을 모두 제공하는가
- 클릭 영역이 올바른 설명을 선택하는가
- 가로/세로 화면에서 잘림, 겹침, 불필요한 스크롤이 없는가
- 흰 배경과 검은 배경 모두에서 강조 표시가 잘 보이는가
- 언어 전환 시 화면과 설명이 함께 바뀌는가
- mock/예정/미연결 범위가 명확히 표시되는가
- README의 범위, 소스 기준, 갱신 트리거, 검증 방법이 현재 산출물과 맞는가
- 실제 브라우저에서 console warning/error가 없는가

## 판단 기준

코드와 캡쳐가 다르면 다음 기준을 따른다.

- 시각적 배치는 캡쳐를 우선한다.
- 동작과 데이터 흐름은 코드를 우선한다.
- 둘이 충돌하면 사용자에게 차이를 설명한다.

사용자가 가이드와 실제 앱을 동일하게 맞추길 원하면, 가이드 수정과 앱 수정 범위를 구분해서 작업한다.
