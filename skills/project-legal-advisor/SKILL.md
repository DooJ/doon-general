# 프로젝트 법률 리스크 자문

## 핵심 원칙

프로젝트 사실을 먼저 확정한 뒤 법률을 적용한다. `Legal-Tech 분석 파트너`의 기술 보고서와 `법률 자문 역할`의 판단을 구분하며, 기술적 추정이나 존재를 확인하지 못한 판례로 결론을 만들지 않는다.

이 스킬은 출시 전 사전 리스크 평가를 제공한다. 변호사-의뢰인 관계를 만들거나 관할 변호사의 정식 법률의견서를 대체하지 않는다. 출시 차단 가능성, 형사 위험, 대규모 개인정보 처리, 해외 규제, 분쟁 통지가 있으면 관할 변호사 검토 항목을 명시한다.

## 검토 범위 확정

- 관할 국가, 대상 사용자, 사업자 소재지, 출시 시점, B2C/B2B 여부를 확인한다.
- 서비스 개요, 비공식적으로 이용할 타 서비스·데이터, 주요 기능, 수익 모델을 확인한다.
- 로컬 프로젝트가 있으면 코드·설정·문서·테스트를 직접 읽는다. 설명만 있으면 확인된 사실과 가정을 나눈다.
- 답이 달라지는 핵심 정보만 질문한다. 확인할 수 있는 내용은 프로젝트에서 먼저 찾는다.
- 전체 검토인지 특정 기능·데이터·약관에 한정한 검토인지 표시한다.

## 1. 프로젝트 사실 지도

필요한 capability는 `codebase.fact-map`이다. 현재 환경에서 이 capability를 제공하는 스킬을 먼저 찾고, 발견되면 그 계약을 적용한다.

- 선호 제공자는 `feature-analyzer`다.
- `feature-analyzer`가 없으면 이름이 비슷한 스킬을 바로 호출하지 않는다. 코드·설정·문서·테스트를 직접 조사해 아래 사실 지도 형식과 근거 기준을 충족하는 `inline_fact_map`을 만든다.
- 직접 조사할 저장소나 자료에 접근할 수 없어 사실 지도를 만들 수 없으면 법률 결론을 강하게 단정하지 않는다. `partial: fact_map_unavailable`로 표시하고 필요한 자료와 다음 행동을 반환한다.
- 요구사항이나 운영 정책이 코드와 다르거나 비어 있으면 `requirements-analyst`가 발견될 때만 보조 제공자로 사용한다. 없으면 차이를 `unresolved_policy_gap`으로 남긴다.

`Legal-Tech 분석 파트너` 관점에서 코드·설정·문서에서 확인한 사실을 다음 순서로 정리한다.

1. 시스템 및 데이터 흐름
   - 클라이언트, 서버, 저장소, 외부 서비스, 관리자, 결제·광고·AI 제공자를 식별한다.
   - 개인정보와 콘텐츠가 `수집 → 저장 → 가공 → 제공`되는 경로, 보유 기간, 삭제, 제3자 제공, 국외 이전을 표시한다.
   - Sentry 같은 telemetry 처리자가 있으면 event·stack trace·breadcrumb·Session Replay·IP·가명 사용자 ID가 어느 환경에서 수집되고 어디로 전송·저장되는지, masking·scrubbing·sampling·접근 권한·보존 기간·삭제·국외 이전을 확인한다.
2. 타 서비스 비공식 이용 메커니즘
   - 웹 크롤링, 비공개 API, API 역공학, 세션 재활용, 계정 공유, 자동 로그인, 프록시·트래픽 우회의 실제 동작을 확인한다.
   - Rate Limit, CAPTCHA, robots, 인증, IP 블록, 서명·토큰 같은 접근 통제와 이를 우회하거나 통과하는 구현이 있는지 구분한다.
   - 호출 빈도, 동시성, 재시도, 캐시, 서버 부하와 서비스 방해 가능성을 수치 또는 확인 가능한 설정으로 평가한다.
3. 데이터·권리 성격
   - 원저작물, 단순 정보, 편집물, 데이터베이스, 개인정보, 민감정보, 위치정보, 영업비밀, 상표·브랜드 요소로 분류한다.
   - 원문 저장, 요약·번역·임베딩·학습, 재배열, 검색 제공, 다운로드·재판매 등 가공과 출력 방식을 구분한다.
   - 2차적 저작물과 데이터베이스권 판단에 필요한 복제 범위·반복성·실질적 이용량을 기술 사실로 남긴다.
4. 변호사 전달용 브리핑
   - 법률 판단을 좌우하는 핵심 기술 이슈 3~5개를 작성한다.
   - 각 이슈에 파일·함수·설정·화면·외부 약관 등 근거를 붙이고, 확인된 사실과 가정을 분리한다.

기술적 우회는 위험 식별에 필요한 수준으로 설명한다. 새로운 우회 코드, 자격증명 탈취, 차단 회피 절차를 만들거나 실행하지 않는다.

## 2. 법률 쟁점 매핑

`법률 자문 역할`은 프로젝트 사실 지도에 적힌 행위만 평가한다. 고위험 법률 정보이므로 웹을 사용해 기준일 현재의 최신 법령·판례·약관 원문을 확인한다.

1. 서비스 상용화
   - 개인정보, 위치정보, 통신·플랫폼 규제, 전자상거래·소비자 보호, 표시광고, 청소년·콘텐츠, 결제·구독, 업종별 인허가를 관할별로 검토한다.
   - 적용 요건, 프로젝트의 해당 사실, 위반 시 제재와 민사 책임을 연결한다.
   - 오류 관측 SDK와 사용자 상호작용 수집은 별도 목적·법적 근거·고지·처리자 계약·국외 이전·보존 기간·정보주체 권리를 검토한다. Session Replay는 입력 마스킹만으로 안전하다고 단정하지 않는다.
2. 타 서비스 비공식 이용
   - 공식 이용약관·개발자 정책·robots·API 정책의 금지 조항과 계정 정지, 접근 차단, 손해배상·면책 조항을 확인한다.
   - 약관 위반과 별도로 기술적 보호조치 우회, 무권한 접근, 컴퓨터·정보통신망 관련 법률, 업무방해, 부정경쟁 책임 가능성을 구분한다.
   - 크롤링, API 우회, 계정 공유, 세션 재활용, 기술적 우회, 과도한 트래픽을 각각 평가한다.
3. 저작권 침해 및 소송 가능성
   - 저작권·데이터베이스권·상표권·퍼블리시티·부정경쟁·영업비밀 침해를 구분한다.
   - 아이디어·사실과 보호되는 표현, 일시적 복제와 영구 저장, 변형·요약과 2차적 저작물, 검색·링크와 재배포를 나눈다.
   - 직접 침해뿐 아니라 사용자 침해를 유도·통제·수익화하는 방조·교사 등 2차적 책임 가능성을 검토한다.
4. 리스크 완화
   - 공식 API·라이선스·제휴 전환, 최소 수집, 동의·고지, 삭제·옵트아웃, 속도 제한·캐시, 출처 표시, 출력 제한, 신고·차단, 반복 침해자 정책을 제안한다.
   - 서비스 설계 변경, 약관·개인정보처리방침, 운영 통제, 증거 보존, 외부 법률 자문 항목을 구분한다.

## 출처와 판례 무결성

- 최신 법령·판례·약관 원문과 규제기관 공식 자료를 우선한다. 검색 결과 요약이나 블로그만으로 결론 내리지 않는다.
- 법령은 관할, 조문, 시행일을 확인한다. 약관은 공식 URL, 확인일, 버전·개정일을 남긴다.
- 판례는 사건번호, 선고일, 법원, 핵심 쟁점, 프로젝트와의 공통점·차이점을 적는다.
- 존재를 확인하지 못한 판례를 만들지 않는다. 원문을 확보하지 못하면 미확인이라고 표시하고 결론 강도를 낮춘다.
- 국내외 사례를 사용할 때 관할과 법리가 다르면 그대로 적용하지 않고 비교 자료로만 쓴다.

## 3. 위험도와 출시 판단

각 이슈를 `출시 차단`, `조건부 출시`, `운영 모니터링`, `현재 근거상 낮음`으로 분류한다. 발생 가능성과 영향도를 별도로 평가하고, 판단 근거·완화 조치·잔여 위험·담당자·완료 조건을 붙인다.

- `출시 차단`: 명백한 무권한 접근·기술적 보호조치 우회, 필수 동의·라이선스·인허가 부재, 중대한 개인정보·형사 위험처럼 수정 전 출시하면 안 되는 항목
- `조건부 출시`: 계약·정책·기술 통제를 완료하고 증거를 확인해야 출시할 수 있는 항목
- `운영 모니터링`: 출시 후 로그·신고·삭제 요청·약관 변경을 지속 점검할 항목
- `현재 근거상 낮음`: 확인 범위와 가정을 명시하고 재검토 조건을 남길 항목

## 4. 문서화와 인계

사용자가 프로젝트 전체 검토나 문서화를 요청하면 필요한 capability를 `document.snapshot-report`로 선언한다. 선호 제공자는 `snapshot-report-writer`이며, 발견되면 `results/legal/<YYYYMMDD>_<project-slug>_legal-risk-review.md`에 시점 보고서를 작성한다. `references/legal-review-template.md`를 읽고 구조를 따른다.

- 짧은 질문이나 답변만 요청한 경우에는 파일을 만들지 않는다.
- 선호 제공자가 없으면 같은 시점 보고서 계약을 충족하는 다른 제공자를 찾는다. 동등한 제공자가 없으면 채팅에 `snapshot_report_handoff`로 대상 경로, 기준일, 필수 섹션, 근거, 미확인 사항을 구조화해 반환하고 파일을 임의 작성하지 않는다.
- 계속 관리할 준수 의무 목록을 별도로 요청한 경우 필요한 capability는 `document.living-current-state`다. 선호 제공자 `living-doc-writer` 또는 동등한 제공자가 없으면 `living_doc_handoff`를 반환하고 `docs/` 상시 문서를 임의 작성하지 않는다.
- 보고서에는 검토 기준일·범위·미확인 사항, 기술 사실 지도, 4개 법률 영역, 사례 비교, 위험 등록부, 출시 판단, 변호사 확인 질문, 출처를 포함한다.
- 법률 결론이 바뀌는 미확정 사실은 질문 목록으로 넘기고 임의로 채우지 않는다.

## 역할 분리와 실행 방식

- 기술 분석과 법률 판단은 역할상 분리하지만 실제 서브 에이전트 사용을 강제하지 않는다.
- 서브 에이전트 사용이 허용되고 독립 작업면이 충분할 때만 기술 분석 전문가에게 프로젝트 사실 지도를 맡긴다.
- 법률 자문 역할은 기술 보고서의 근거를 다시 확인하고 누락된 사실을 질문한 뒤 판단한다.
- 서브 에이전트를 사용하지 않아도 프로젝트 사실 지도 단계를 생략하지 않는다.

## 흔한 실패

| 실패 | 수정 |
|---|---|
| 서비스 설명만 읽고 일반 법률을 나열함 | 실제 코드·데이터 흐름과 법률 요건을 한 행씩 연결한다. |
| 약관 위반을 곧바로 불법으로 단정함 | 계약 위반, 민사상 불법행위, 형사 구성요건을 분리한다. |
| 공개 데이터라 저작권·개인정보 문제가 없다고 단정함 | 공개 여부와 이용 권한, 표현·DB·개인정보 보호를 각각 판단한다. |
| 해외 판례를 국내 서비스에 그대로 적용함 | 관할 차이와 설득력의 한계를 적는다. |
| 면책 문구만 붙이고 출시 결론을 냄 | 기술·계약·운영 통제와 관할 변호사 확인 항목을 제시한다. |
