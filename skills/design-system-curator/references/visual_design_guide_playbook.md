# 시각 디자인 가이드 제작 기준

웹·앱의 디자인 가이드에서 컴포넌트를 **눈으로 비교하고 상태를 확인**해야 할 때 적용한다. `DESIGN.md` 작성만 요청된 경우에는 [DESIGN.md 작성 기준](./design_md_playbook.md)을 따른다. 출력 형식은 사용자가 지정한 도구를 우선하고, 도구 지정이 없는 웹 가이드는 브라우저에서 열 수 있는 HTML/Storybook 같은 렌더링 가능한 산출물을 기본으로 한다.

## 세 산출물의 역할

| 산출물 | 담는 정보 | 완료 판단 |
|---|---|---|
| `DESIGN.md` | 대상 사용자, 브랜드 근거, 색·서체·간격 토큰, 원칙과 예외 | 확정값은 제품 코드·자산과 일치하고 미정값은 후보로 표시하며, 시각 가이드가 있으면 연결됨 |
| 상세 디자인 가이드 | 화면 흐름, 컴포넌트 치수·구조·변형·상태, 반응형·접근성·구현 상태 | 실제 화면을 만들 수 있을 만큼 구체적이며 시각 예시와 연결됨 |
| 시각 컴포넌트 가이드 | 제품에서 실제 쓰는 브랜드 요소·글자·컴포넌트·상태의 렌더링된 예시 | 사용자가 열어 비교할 수 있고 대표 상태와 좁은 화면을 확인함 |

문서 파일의 이름은 프로젝트 관례를 따른다. 산출물의 이름이 같아도 역할은 섞지 않는다. Markdown 표는 치수와 판단 근거를 전달하지만, 렌더링된 외형의 검증을 대신하지 않는다.

## 근거 수집과 충돌 해결

1. 기존 제품은 사용자가 승인한 현재 시안과 최신 브랜드 원본을 찾는다. 로고 원본, 앱의 로그인·인트로, 실제 웹 CSS, 컴포넌트 구현을 직접 확인한다. 신규 제품은 먼저 선택된 콘셉트와 대상 사용자·화면 목적을 근거로 삼는다. 방향이 아직 선택되지 않았다면 `ui-concept-director`의 콘셉트 탐색을 먼저 거친다.
2. 과거 토큰과 새 자산이 함께 남아 있다면 사용자의 명시적 방향, 현재 사용 화면과 원본 자산을 대조한다. 오래된 공통 색상 상수 하나만으로 브랜드를 확정하지 않는다.
3. 색은 브랜드·동작·표면·텍스트·경계·상태 역할로 나눈다. 고객이 업로드한 콘텐츠의 색을 제품 UI 토큰으로 오인하지 않는다.
4. 문서 규칙과 실제 CSS가 다른 값은 `현재 시안`, `확정 규칙`, `추가 구현`으로 나눠 기록한다. 미구현 상태를 이미 작동하는 것처럼 보여주지 않는다.
5. 승인된 로고·토큰·컴포넌트가 없으면 가상의 확정 자산을 만들지 않는다. 필요한 예시는 출처와 함께 `후보` 또는 `미정`으로 표시하고, 실제 제품에서 쓰지 않는 컴포넌트는 전시 범위에서 제외한다.

## 화면에 전시할 최소 항목

아래 항목은 제품에 존재하거나 선택된 방향에서 필요한 경우에만 전시한다. 로고, 카드, 목록, 폼, 파일 첨부가 없는 제품에 이를 채우기 위한 예시를 추가하지 않는다.

- **브랜드:** 밝은/어두운 배경의 실제 로고, 주요 색상 견본과 값, 색상 역할.
- **글자:** 대표·페이지·섹션·카드 타이틀, 본문과 메타 문구. 실제 서비스 문장을 사용하고 긴 이름의 줄바꿈을 확인한다.
- **형태:** spacing scale, radius, 구분선, 표면과 필요할 때 그림자.
- **버튼:** 주요·보조·텍스트/아이콘 변형과 기본·hover·focus·disabled·loading. 정적 예시라도 각 상태가 구분되게 배치한다.
- **카드·목록:** 실제 화면의 이미지/상태/메타 순서, 선택·hover, 빈 목록, 많은 항목과 검색.
- **입력·피드백:** 라벨·도움말·오류, 파일 첨부, 결과·운영 상태. 색과 함께 이유·상태명을 쓴다.
- **맥락:** 어떤 화면에서 쓰이는지 링크나 짧은 설명. 데모가 실제 저장·배포를 하지 않으면 그 사실을 표시한다.

페이지 구조는 목차 → 브랜드/기초 → 컴포넌트 → 상태/반응형 순서가 읽기 쉽다. 예시가 제품과 동떨어진 별도 미감이 되지 않도록 가능한 경우 제품 CSS 변수, 컴포넌트 코드와 자산을 재사용한다. 재사용이 어렵다면 값의 중복과 동기화 책임을 문서에 적는다.

## 제작과 검증

1. 기존 제품은 현재 화면에서 반복 컴포넌트를 추출한다. 신규 제품은 선택된 콘셉트의 핵심 화면에서 필요한 컴포넌트를 고른다. 예시는 실제 사용 상황의 문구·데이터로 채우고 미확정 값은 후보라고 표시한다.
2. 키보드 focus, 선택, 검색, 파일 선택 등 가이드에서 확인할 핵심 동작만 구현한다. 시각용 데모의 버튼이 실제 저장을 수행하는 것처럼 보이지 않게 한다.
3. `DESIGN.md`와 상세 가이드에서 시각 페이지로, 시각 페이지에서 문서·제품 화면으로 이동할 수 있게 연결한다.
4. 데스크톱과 모바일을 실제 브라우저/플랫폼에서 렌더링한다. 적용되는 항목의 로고 로드, 글자 잘림, 가로 넘침, 상태 대비, focus, 빈 결과, 이미지 비율을 확인한다. 신규 제품은 후보 값이 확정값처럼 표시되지 않았는지도 확인한다.
5. 최종 링크와 대표 스크린샷을 사용자에게 보여준다. 문서만 만들거나 HTML 파일만 저장한 상태를 시각 검수 완료로 간주하지 않는다.

## 보이미 고객 웹에서 얻은 참고 사례 · 2026-10-02

- **근거:** 매니저 앱의 로그인·인트로와 새 워드마크에서 파랑 `#425CC7`을 확인했다. 앱의 오래된 공통 색상 파일에는 이전 빨강이 남아 있어 시안에 그대로 쓰지 않았다.
- **문서 분리:** `DESIGN.md`에는 브랜드·토큰·원칙, `DESIGN-GUIDE.md`에는 화면 흐름과 컴포넌트의 치수·구조·상태를 담았다.
- **시각 확인:** 브라우저 가이드에 실제 로고와 색상 견본, 제목 단계, 버튼 상태, 운영 화면 카드와 방식 선택 카드, 검색 목록·객체 목록·입력·피드백을 렌더링했다.
- **연결과 QA:** 가이드와 두 문서를 서로 연결하고, 화면 폭별 가로 넘침과 검색·선택·파일 예시 동작을 확인했다. 실제 API 저장과 장비 반영은 데모 범위 밖이라고 표시했다.

이 사례의 파일명, 색상 값과 문구는 **사례의 근거**다. 다른 제품에 복사할 디자인 토큰이나 표준 컴포넌트 값이 아니다. 새 작업에서는 그 제품의 승인된 자산과 실제 구현을 다시 조사한다.
