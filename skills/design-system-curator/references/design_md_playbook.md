# DESIGN.md 작성 기준

조회일: 2026-10-01

이 자료는 사용자가 `DESIGN.md` 생성이나 보완을 요청한 경우에만 적용한다. 형식은 [Google Labs의 DESIGN.md 명세](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md)와 [설계 철학](https://github.com/google-labs-code/design.md/blob/main/PHILOSOPHY.md)을 참고한다. 명세는 현재 alpha 단계이므로 도구 호환이 필요한 작업에서는 사용 시점의 규칙을 다시 확인한다. [designmd.app](https://designmd.app/)의 예시는 방향 탐색에 활용하되, 예시 문구와 값은 제품의 확정 규칙으로 간주하지 않는다.

## 작성 입력

- 기존 제품은 실제 화면, 코드의 색·서체·간격·컴포넌트, 브랜드 자산과 기존 디자인 문서를 먼저 확인한다. 신규 제품은 선택된 콘셉트와 핵심 화면을 근거로 삼고, 승인되지 않은 값은 후보로 표시한다.
- 아직 결정되지 않은 값은 확정값처럼 채우지 않고 `미정` 또는 검증할 후보로 표시한다.
- Apple HIG나 Material 3 같은 플랫폼 기준, Mobbin 같은 실제 사례, daisyUI 같은 구현 라이브러리의 역할을 구분한다. 외부 사례에서 관찰한 구조와 현재 제품에 적용한 결정을 연결한다.

## 문서 구성

- 짧은 개요에 대상 사용자, 제품의 성격, 시각적 태도, 우선 행동, 피할 표현을 서술한다.
- 반복되는 확정값은 색상 역할, 서체, 간격, 모서리, 필요할 때 컴포넌트 값으로 정리한다. 기계 판독이 필요하면 명세의 선택적 YAML frontmatter를 사용하고, Markdown 본문에는 값의 사용 이유와 예외를 쓴다.
- 주요 컴포넌트마다 용도, 변형, 상태, 레이블·키보드·터치 기준, 반응형 동작을 기록한다. 필요한 정보가 방대하면 별도 컴포넌트 문서로 연결한다.
- 아이콘은 선택한 기본 세트와 크기·획·채움·접근성 규칙을 적는다. 특정 세트가 아직 선택되지 않았다면 후보와 판단 기준만 남긴다.
- 모션은 목적, 지속 시간 범위, 완급, 축소 동작을 정의한다. 구현 라이브러리 이름은 실제 선택된 경우에만 적는다.
- 레퍼런스 URL을 쌓는 대신 `관찰 → 채택/배제 이유 → 우리 제품의 규칙`을 기록한다.

## 시각 가이드와의 관계

`DESIGN.md`는 디자인 결정과 토큰의 텍스트 기준이다. 사용자가 버튼 모양, 카드 구조, 목록 행, 타이틀 위계를 눈으로 확인하려는 경우 Markdown 표만으로는 충분하지 않다. 웹은 HTML/Storybook처럼 브라우저에서 볼 수 있는 컴포넌트 가이드, 앱은 플랫폼 미리보기 등을 함께 제공한다. 시각 가이드의 자세한 절차는 [시각 디자인 가이드 제작 기준](./visual_design_guide_playbook.md)을 따른다.

- `DESIGN.md`에는 브랜드 출처, 확정 토큰, 컴포넌트의 역할과 사용 원칙, 시각 가이드 링크를 둔다.
- 상세 가이드 문서에는 치수, 변형, 상태, 반응형과 구현 여부를 적고 시각 예시와 양방향으로 연결한다.
- 시각 예시는 같은 자산과 토큰을 사용한다. 서로 다른 값을 보이면 실제 승인된 최신 브랜드 자산과 제품 화면을 대조해 한쪽을 수정한다.
- 단순히 `DESIGN.md`라는 이름을 요청한 경우 시각 페이지 생성까지 임의로 확장하지 않는다. 사용자가 디자인 가이드의 시각적 확인을 요청했거나 산출물에 명시했을 때 함께 만든다.

## 활용 가능성 검증

1. YAML 값과 본문 설명, 컴포넌트 예시가 서로 모순되지 않는지 확인한다.
2. 기존 제품의 실제 화면 또는 신규 제품의 선택된 콘셉트 화면 하나 이상에 규칙을 적용해 정보 위계, 긴 텍스트, 빈 데이터, 오류, 좁은 화면, 포커스 상태를 검토한다. 시각 가이드가 있으면 문서와 렌더링 결과를 함께 대조한다.
3. 기존 코드의 토큰·컴포넌트와 다른 경우 변경 범위와 이행 순서를 적는다.
4. 명세 호환이 요구되고 CLI 사용이 가능한 환경이면 공식 저장소의 lint 명령으로 형식도 검사한다. 형식 검사는 실제 UI 품질 검토를 대신하지 않는다.

`DESIGN.md`는 일관된 결정을 전달하는 기준 문서다. 구현 가능한 수준은 실제 화면과 코드에 대입해 확인하며, 파일만 작성했다는 이유로 완성된 디자인 시스템이라고 판단하지 않는다.
