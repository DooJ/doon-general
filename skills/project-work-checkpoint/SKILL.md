# 프로젝트 작업 상태 정리

작업을 단위로 현재 유효한 상태를 보존합니다. 한 대화의 요청·응답을 순서대로 옮겨 적지 않습니다. 커밋과 대화 중단은 각각 상태를 확인할 **중단점**이며, 어느 것도 단독으로 작업 완료를 뜻하지 않습니다.

## 발동과 경계

- 이후 실행에서 재개할 미완료 상태, 오래 유효할 결정이나 중요한 완료 결과가 생긴 채 응답을 마치거나 작업을 중단할 때, 추적 중인 작업의 관련 Git 커밋을 만들거나 발견했을 때, 기존 작업을 재개할 때 적용합니다.
- 짧은 질문, 한 번에 끝난 사소한 수정, 상태 변화가 없는 대화, 단순 주제 변경, 관련 없는 커밋에는 새 작업 항목을 만들지 않습니다. 응답마다 갱신 필요 여부는 가볍게 판단하되, 실제 쓰기는 재개 가치가 있는 변화가 있을 때만 합니다.
- 이 스킬은 호출됐을 때 상태를 대조합니다. 에이전트가 실행되지 않는 동안의 대화 종료·외부 커밋을 실시간 감지하는 후크가 아닙니다. 다음 재개 시 마지막 기록 이후의 Git 상태를 확인해 놓친 중단점을 복구합니다.
- 사용자 선호는 `user-style-memory`, 스레드 전환과 짧은 런타임 복구 상태는 `task_continuity`, 계속 유효한 요구사항·API·운영 설명은 `living-doc-writer`, 회의·팀의 장기 gate 운영은 Huggies가 맡습니다. 이 스킬은 프로젝트에 남겨 둘 개별 작업 상태만 다룹니다.

## 기록 위치와 원본

1. 현재 `PROJECT_ROOT`를 확인하고, 기존 작업 상태·진행 문서와 프로젝트의 문서 관례를 먼저 찾습니다. 동일한 작업을 다루는 문서가 있으면 이름이나 경로를 바꾸지 않고 그 항목을 갱신합니다.
2. 별도 관례가 없는 Git 프로젝트에서는 `docs/work-checkpoints.md`를 기본으로 합니다. 프로젝트가 `publish/`를 작업 상태의 원본으로 쓰거나 사용자가 경로를 지정했다면 그 위치를 따릅니다. 일반 프로젝트의 상태를 전역 DooN 루트나 사용자 스타일 메모리에 저장하지 않습니다.
3. Notion·Git·Linear 연결형 추적이 활성화돼 있으면 계획·마일스톤은 Notion, 구현·기술 문서는 Git, 판정된 이슈·QA는 Linear의 원본 책임을 유지합니다. 작업 항목에는 필요한 상태와 원본 링크만 두고 전문을 복제하지 않습니다.

## 대조와 갱신

1. **작업 식별:** 기존 Work ID·이슈·PR 식별자를 우선 사용합니다. 없으면 프로젝트 안에서 안정적인 작업 ID를 정하고 제목 변경이나 후속 대화에도 재사용합니다. 커밋 SHA와 대화 시각은 중단점이지 작업 ID가 아닙니다.
2. **이전 상태 확인:** 해당 항목의 목표, 마지막 기준 Git 브랜치·커밋, 검증 상태, 남은 일과 다음 행동을 읽습니다. 문서가 없고 이후 실행에도 유효한 상태가 있을 때만 현재 작업의 확인된 사실로 첫 항목을 만듭니다. 과거 대화·커밋을 일괄 소급 기록하지 않습니다.
3. **현재 근거 확인:** 이번 요청과 정정, 실제 산출물, 테스트·리뷰 결과를 대조합니다. Git 프로젝트라면 작업 트리와 관련 커밋의 변경 범위를 확인합니다. 마지막 기록 이후의 커밋도 살피되, 관련성이 확인된 변경만 이 작업에 연결합니다. 커밋 메시지만으로 의도·완료·검증을 추정하지 않습니다.
4. **상태 판정:** 작업 상태(`진행 중`, `중단`, `검증 대기`, `차단`, `완료`, `취소`)와 검증 상태(`통과`, `실패`, `미실행`, `일부 확인`, `판정 불가`)를 별도로 기록합니다. 커밋이 있어도 후속 작업이 남으면 완료로 닫지 않습니다. 검증을 건너뛰거나 실행하지 못했다면 그 사실과 다음 확인 행동을 남깁니다. 완료는 현재 합의된 요청 범위의 성공 조건을 충족했을 때만 판정하고, 검증을 생략한 결과를 검증 완료로 표현하지 않습니다. 사용자가 미완료 작업을 멈추거나 취소하면 각각 `중단` 또는 `취소`로 둡니다.
5. **같은 항목 갱신:** 새 사실만 반영합니다. 완료 결과와 검증 근거, 남은 일, 재개 시 첫 행동, 관련 커밋·PR·문서 링크를 짧게 유지합니다. 같은 커밋이나 중단점을 다시 만나도 항목을 복제하지 않습니다. 완료된 오래된 항목은 결과 링크 중심으로 압축하고 열린 작업의 재개 정보는 보존합니다.
6. **재개:** 기존 문서의 다음 행동부터 시작하되 현재 Git 브랜치·HEAD·작업 트리와 필요한 외부 이슈 상태를 다시 확인합니다. 기록과 현재 상태가 다르면 실제 근거를 확인해 갱신하고, 알 수 없는 부분은 `판정 불가`로 둡니다.

## 항목의 최소 형식

기존 문서의 형식을 우선합니다. 새 문서라면 각 작업에 다음 정보만 둡니다.

| 항목 | 기록 내용 |
|---|---|
| 작업 ID·목표 | 현재 요청 범위와 성공 조건 |
| 현재 상태 | 작업 상태와 별도의 검증 상태 |
| 확인된 결과 | 실제 바뀐 기능·문서·결정과 근거 |
| 마지막 중단점 | 관련 대화의 최종 확인일, 브랜치·커밋 또는 미커밋 변경 여부 |
| 남은 일·다음 행동 | 미검증·차단 사유와 재개 직후 확인할 한 단계 |
| 연결 | 관련 코드·문서·PR·이슈 링크 |

비밀값, 대화 원문, 중간 추측, 테스트 로그 전문은 옮기지 않습니다. 기록을 갱신한 직후 새 커밋을 강제하지 않습니다. 커밋 후 SHA를 추적 문서에 적으면 새 미커밋 변경이 생길 수 있으므로, 그 변경을 숨기거나 상태 기록만을 위해 반복 커밋하지 말고 현재 작업 트리 상태로 명확히 보고합니다.

## 확인

- 기록의 완료·검증 표현이 실제 증거와 일치하는지 확인합니다.
- 기존 항목의 미완료 사항을 조용히 지우거나 다른 작업의 커밋을 연결하지 않습니다.
- 문서가 실질적으로 바뀌지 않았다면 파일을 다시 쓰지 않습니다.
- 최종 보고에는 갱신한 작업 상태 문서의 위치와 아직 남은 확인 사항만 간단히 알립니다.
