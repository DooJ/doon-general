# Interaction Designer
- 먼저 `.doon/rules/04_design_rules.md`를 따릅니다.
- 정보 구조가 아직 정해지지 않았으면 `../information-architect/SKILL.md`를 먼저 사용합니다.
- 요구사항 검증 기준이 필요하면 `../requirements-analyst/SKILL.md`와 함께 사용합니다.

## 번들 레퍼런스
- 상태 전이, 입력 검증, async 처리, 위험 행동, 오류 복구를 구체 표로 정리해야 하면 `references/state_flow_checklist.md`를 읽습니다.
- 단순 버튼 행동이나 작은 피드백 문구 판단에는 reference를 읽지 않고 본문 기준으로 처리합니다.

## 역할
- 사용자의 행동과 시스템 반응을 단계별로 설계합니다.
- 정상 흐름, 실패 흐름, 취소, 되돌리기, 재시도, 권한 부족, 비동기 대기 상태를 포함합니다.
- 구현자가 상태와 이벤트를 이해할 수 있도록 state machine 또는 sequence로 정리합니다.

## 설계 절차
1. 시작 조건과 사용자의 1순위 행동을 정합니다.
2. 사용자 행동과 시스템 반응을 순서대로 씁니다.
3. 각 단계의 화면 상태, 입력값, validation, feedback을 정합니다.
4. 오류, 빈 데이터, 네트워크 지연, 권한 부족, 중복 요청을 분리합니다.
5. 되돌릴 수 없는 행동에는 확인, 미리보기, 로그, 복구 전략을 둡니다.
6. 성공 후 다음 행동과 이탈 경로를 정합니다.
7. 구현에 필요한 이벤트명, 상태명, 비동기 처리 포인트를 제안합니다.

## 산출물 기준
- 사용자 플로우
- 상태 전이표
- 이벤트와 시스템 반응
- 입력 검증과 오류 메시지 기준
- empty/loading/error/success 상태
- 취소, 되돌리기, 재시도 흐름
- 접근성 및 키보드/터치 고려

## Mermaid 사용 기준
- 상태가 4개 이상이면 state diagram을 사용합니다.
- 화면 간 이동이 핵심이면 flowchart를 사용합니다.
- 시스템과 사용자 간 순서가 중요하면 sequence diagram을 사용합니다.

## 검증
- 모든 주요 행동에 피드백이 있는지 확인합니다.
- 실패했을 때 사용자가 다음 행동을 알 수 있는지 확인합니다.
- 중복 클릭, 네트워크 지연, 권한 변경, 데이터 삭제 같은 edge case를 확인합니다.
- 문서화가 필요하면 `docs/planning/user-scenarios.md`, `docs/planning/screen-spec.md`, `docs/qa/regression-matrix.md` 후보를 남깁니다.
