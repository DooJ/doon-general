# UI Concept Director

- 이 스킬은 새 화면을 실제로 그리기 전의 **방향 탐색, 레퍼런스 선택, 첫 시안 설계, 피드백 반복**을 담당합니다.
- `DESIGN.md` 생성, 토큰 파일 작성, 브랜드 시스템 문서화는 이 스킬의 기본 산출물이 아닙니다. 사용자가 별도로 요청하기 전까지 만들지 않습니다.
- 확정된 방향을 구체적인 token, component state, responsive rule, handoff로 다듬어야 하면 `../design-generalist/SKILL.md`의 기준을 함께 적용합니다.

## 이 스킬의 역할

- 사용자의 화면 목적을 듣고 핵심 행동, 정보 우선순위, 플랫폼 맥락을 빠르게 구조화합니다.
- 현재 프로젝트의 기존 UI, CSS, 컴포넌트, 스크린샷이 있으면 먼저 읽고 연속성을 확인합니다.
- 기존 기준이 부족하면 공개 디자인 시스템, 제품 유형별 패턴, 도메인 관습, 플랫폼 가이드를 레퍼런스 후보로 삼습니다.
- 플랫폼 선택과 샘플 레퍼런스가 필요하면 `../design-generalist/references/platform_reference_matrix.md`를 읽고, 웹 작업은 `.doon/rules/05_web_design_rules.md`, 앱 작업은 `.doon/rules/06_app_design_rules.md`를 함께 적용합니다.
- 레퍼런스 후보는 목적별로 나눕니다. Mobbin은 실제 앱/Web App flow, Awwwards는 브랜드 웹과 인터랙션, Dribbble은 컴포넌트/비주얼 polish, Behance는 UX case study와 브랜딩 프로세스, Land-book은 SaaS/AI/스타트업 랜딩 구조를 볼 때 우선합니다.
- 레퍼런스는 복제 대상이 아니라 **판단 재료**로 사용합니다. 색상만 베끼지 말고 정보 밀도, 레이아웃 흐름, 컴포넌트 선택, 상호작용 태도까지 해석합니다.
- 레퍼런스를 실제로 검색하거나 특정 화면/케이스를 근거로 삼으면 `../design-generalist/references/reference_evidence_log.md` 기준으로 검색어, URL/title, 관찰 요소, 반영/배제 결정을 남깁니다.
- 사용자가 별도 레퍼런스를 주지 않았더라도 모든 서비스를 같은 카드형 SaaS 화면으로 수렴시키지 않고, 서비스 도메인과 사용 맥락에 맞는 형태 차이를 먼저 탐색합니다.
- 2~3개의 서로 다른 콘셉트 방향을 제시한 뒤, 그중 하나를 기준으로 첫 화면 초안을 만듭니다.
- 사용자의 피드백을 `정보 위계`, `위치`, `강조`, `컴포넌트`, `톤`, `반응형` 관점으로 분해해 다음 버전에 반영합니다.

## 기본 워크플로우

1. 화면의 의도를 잡습니다.
   - 화면 이름 또는 기능
   - 사용자가 이 화면에서 해야 할 1순위 행동
   - 보조 행동과 없어도 되는 행동
   - 보여줄 데이터의 양과 변동성
   - 웹, 모바일, 대시보드, 운영툴, 랜딩, 설정 화면 등 표면 유형
   - 사용자의 숙련도, 반복 사용 빈도, 실수 비용
   - 서비스 도메인과 감정 톤: 신뢰, 속도, 재미, 몰입, 편집감, 전문성, 친근함 중 무엇이 중요한지
2. 기존 맥락을 확인합니다.
   - 현재 프로젝트의 디자인 언어, 컴포넌트, 색상, spacing, density, copy tone을 먼저 확인합니다.
   - 스크린샷이나 실제 화면이 있으면 말보다 화면을 우선합니다.
   - 코드 구현이 예상되면 현재 프론트엔드 스택, UI 라이브러리, CSS 구조를 확인합니다.
3. 레퍼런스 방향을 고릅니다.
   - 현재 제품과 가장 가까운 내부 레퍼런스
   - 같은 도메인 또는 같은 표면 유형의 UI 패턴
   - 공개 디자인 시스템이나 제품 디자인에서 가져올 수 있는 구조적 힌트
   - 플랫폼 기본 기대치(Material, Apple, web admin, SaaS dashboard 등)
   - SaaS/admin/dashboard/app flow는 Mobbin, landing/AI startup은 Land-book, brand interaction은 Awwwards, component polish는 Dribbble, UX process/branding rationale은 Behance를 우선 검토합니다.
   - 초기 시안이나 리디자인은 최소 2개 이상의 구조적으로 다른 레퍼런스 방향
   - 최신 공개 레퍼런스가 중요하면 웹 검색으로 현재성을 확인하고 출처를 남깁니다.
   - 검색 기반 레퍼런스라면 사용한 검색어와 선택한 후보를 기록하고, 실제 화면을 확인하지 못했으면 `실화면 미확인`으로 표시합니다.
4. 콘셉트 후보를 만듭니다.
   - 보통 2~3개로 제한합니다.
   - 각 후보는 색상 취향이 아니라 `정보 구조`, `밀도`, `주요 행동 위치`, `탐색 방식`, `시각적 태도`가 달라야 합니다.
   - 후보 중 최소 1개는 기본적인 SaaS/카드형 접근과 다른 구조적 대안을 포함합니다.
   - 후보마다 적합한 이유, 버릴 이유, 구현 난이도를 함께 적습니다.
5. 첫 화면 초안을 제시합니다.
   - 완성안처럼 과장하지 말고, 사용자가 포지션을 바꾸며 판단할 수 있는 초안으로 만듭니다.
   - 핵심 영역 배치, CTA 위치, 주요 데이터 그룹, empty/loading/error 위치, mobile/desktop 차이를 포함합니다.
   - 가능하면 실제 label과 예시 데이터를 사용합니다.
6. 피드백을 받아 반복합니다.
   - “이걸 위로”, “이게 더 중요해”, “카드 말고 리스트”, “더 고급스럽게” 같은 피드백을 디자인 변수로 번역합니다.
   - 바뀐 의도를 요약한 뒤 다음 버전에서 무엇을 바꾸는지 명확히 합니다.

## 레퍼런스 선택 기준

- **기존 제품 우선**: 이미 앱 안에 화면이 있으면 그 언어를 먼저 확장합니다.
- **표면 유형 우선**: 운영툴은 처리 속도와 오류 방지, 랜딩은 메시지와 신뢰, 모바일은 집중 흐름과 터치, 대시보드는 비교와 상태 가시성을 우선합니다.
- **도메인 우선**: 금융, 건강, 교육, 여행, 개발자 도구처럼 도메인 기대치가 강하면 무드보다 사용자의 신뢰와 실수를 먼저 봅니다.
- **서비스 형태 우선**: 커머스, 콘텐츠, 커뮤니티, 예약, 생산성, AI 자동화, 금융, 교육, 엔터테인먼트는 같은 컴포넌트를 쓰더라도 탐색, 비교, 입력, 피드백의 중심이 달라야 합니다.
- **차별점 확인**: 참고 디자인을 그대로 따라 하지 말고, 이 화면만의 독자적 행동과 정보 구조를 찾아냅니다.
- **구현 가능성 확인**: 현 코드베이스가 감당하기 어려운 motion, 3D, 과한 이미지 시스템은 초안 단계에서 리스크로 표시합니다.

## 콘셉트 후보 형식

각 후보는 아래 항목으로 짧고 비교 가능하게 작성합니다.

- `이름`: 사용자가 기억하기 쉬운 방향명
- `잘 맞는 이유`: 화면 목적과 연결되는 근거
- `정보 구조`: 주요 영역과 우선순위
- `시각 언어`: 색, 타이포, 여백, 밀도, 표면 처리의 큰 방향
- `상호작용`: CTA, 필터, 입력, 단계 이동, 피드백 방식
- `주의점`: 이 방향이 실패할 수 있는 조건
- `구현 난이도`: 낮음, 중간, 높음

## 첫 화면 초안 형식

사용자가 바로 위치를 바꾸며 피드백할 수 있도록 아래 순서를 기본으로 합니다.

- `목적과 가정`: 아직 모르는 것은 가정으로 표시합니다.
- `추천 방향`: 선택한 콘셉트 1개와 이유를 적습니다.
- `레퍼런스 근거`: 실제 검색/열람한 자료가 있으면 검색어, URL/title, 관찰 요소, 반영/배제 결정을 적습니다.
- `레이아웃 초안`: desktop/mobile 중 요청 표면에 맞춰 영역 배치를 텍스트 wireframe으로 보여줍니다.
- `주요 컴포넌트`: header, navigation, primary CTA, content group, form, table, card, modal 등.
- `상태`: empty/loading/error/success, permission, disabled, validation.
- `조정 질문`: 다음 반복에서 사용자가 판단해야 할 2~4개 질문.

예시:

```markdown
## 1안: 작업 중심 대시보드
- 잘 맞는 이유: 사용자가 반복적으로 상태를 확인하고 빠르게 처리해야 함
- 정보 구조: 상단 요약 → 필터 → 리스트/테이블 → 우측 상세 패널
- 시각 언어: 저채도 배경, 강한 상태 배지, 촘촘한 spacing
- 주의점: 첫 사용자에게는 다소 차갑고 복잡해 보일 수 있음

초안:
[Top bar: 화면명 / 검색 / 주요 액션]
[Summary strip: 핵심 지표 3개]
[Filter row: 상태, 기간, 담당자]
[Main: 데이터 테이블]
[Right drawer: 선택 항목 상세 + 승인/반려]
```

## 반복 조정 규칙

- 사용자의 피드백을 그대로 반영하기 전에 어떤 디자인 의도 변화인지 짧게 해석합니다.
- 위치 변경은 정보 우선순위 변화로 보고, 영향을 받는 주변 요소까지 함께 조정합니다.
- “더 예쁘게”는 색상 변경보다 hierarchy, 여백, type scale, contrast, component rhythm을 먼저 손봅니다.
- “더 고급스럽게”는 장식 추가보다 밀도 조절, 색상 절제, 타이포 위계, 표면 질서를 먼저 봅니다.
- “더 직관적으로”는 CTA 위치, 레이블, 단계 수, 오류 예방, progressive disclosure를 먼저 봅니다.
- 초안이 확정되기 전에는 세부 token이나 장기 디자인 문서에 시간을 쓰지 않습니다.

## 출력 원칙

- 처음부터 최종안처럼 단정하지 말고, 비교 가능한 선택지와 추천안을 함께 둡니다.
- 참고 디자인 이름을 언급할 때는 무엇을 참고하는지 구체화합니다. 예: 색감, 정보 밀도, 카드 구조, navigation, editorial rhythm.
- 레퍼런스 사이트를 언급할 때는 `반영할 요소`와 `버릴 요소`를 같이 적어 복제처럼 보이지 않게 합니다.
- 실제 레퍼런스 탐색 없이 도메인 관습만 사용했다면 그렇게 표시하고, 자료를 본 것처럼 URL이나 검색어를 만들지 않습니다.
- 별도 레퍼런스를 사용하지 않았다면 어떤 서비스 유형과 도메인 관습을 기준으로 삼았는지 명시합니다.
- 출처 없는 “요즘 스타일” 같은 표현은 피하고, 관찰 가능한 UI 특성으로 설명합니다.
- 사용자가 바로 피드백할 수 있게 “다음에 바꿀 수 있는 지점”을 명시합니다.
- `DESIGN.md`를 만들거나 저장하지 않습니다.
