# 여행 숙소 검색

## 역할과 발동 경계

사용자가 "아속역 근처 호텔만 추천", "가족 4명 숙소 비교", "예약한 호텔 위치 괜찮아?"처럼 숙소 선택만 요청하면 사용합니다. 권역과 실제 숙소 후보를 비교하지만 항공편, 식당 목록 또는 날짜별 전체 여행 일정을 강제로 만들지 않습니다.

`travel-planner`의 전체 계획에서는 목적지 정보와 항공 조사와 병렬로 실행할 수 있는 worker입니다. 숙소만 필요한 부분 요청이면 이 스킬에서 끝내며, 사용자가 요구하지 않은 일정 합성으로 범위를 넓히지 않습니다.

## 필요한 입력

- 도시와 희망 권역 또는 주요 방문 목적
- 체크인·체크아웃 날짜와 숙박 수
- 객실 수, 성인·아동 인원, 침대·커넥팅룸 요구
- 1박 또는 전체 예산과 표시 통화
- 호텔 등급, 조식, 수영장, 세탁, 욕조 등 필수 시설
- 대중교통·택시 선호와 허용 도보량
- 무료 취소, 선결제, 보증금에 대한 선호
- 확정 숙소와 변경 가능 여부
- 오케스트레이션 작업이면 `task_id`, `context_revision`, 의존 입력

날짜·인원·객실 수가 없어 실제 객실 가격을 비교할 수 없으면 권역 차이와 대표 숙소 예시를 제공하고 `partial`로 표시합니다. worker 실행 중에는 사용자에게 독립적으로 질문하지 않고 `unresolved_questions`에 남깁니다.

## 권역 추천 후 다음 동작

숙박 권역만 추천하고 종료하지 않습니다. 다음 둘 중 하나로 이어갑니다.

1. 날짜와 인원이 충분하면 권역별 대표 숙소를 우선 2~3개씩 실제 검색합니다. 실제 숙소의 객실 정원, 실제 가격, 세금, 무료 취소, 체크인·짐 보관과 교통을 같은 기준으로 비교합니다.
2. 권역 선택이 숙소 결과를 크게 바꾸면 각 권역 차이를 이동, 분위기, 소음, 야간 활동, 가격대, 핵심 장소 접근으로 설명하고 선택 질문 하나를 합니다. 답을 기다리는 동안에는 권역별 대표 숙소 예시를 가격 확정이 아닌 `candidate`로 제시할 수 있습니다.

전체 계획을 바로 초안으로 제공해야 하면 가장 균형적인 권역 하나를 명시적 일반 가정으로 선택하고, 그 권역의 대표 숙소를 검색합니다. 사용자가 권역을 바꾸면 기존 결과를 `freshness: stale`로 전환해 다시 조회합니다.

### 선택과 확정 경계

- 사용자 명시 선택 전에는 권역과 모든 실제 숙소를 `candidate`로 유지합니다.
- 사용자가 "아속으로 볼게"처럼 권역만 고르면 권역은 `selected`지만 그 안의 호텔은 계속 `candidate`입니다.
- 사용자가 특정 숙소를 고르면 해당 숙소를 `selected`로 바꾸고 일정·교통·비용 영향을 갱신합니다.
- 예약번호, 바우처, 결제 완료 같은 예약 증거를 사용자가 제공하기 전에는 `booked`로 바꾸지 않습니다.
- 에이전트의 종합 추천, 가장 균형적인 후보, 최저가 후보를 사용자 선택으로 간주하거나 자동 확정하지 않습니다.
- 비교표 끝에는 사용자가 다음 대화에서 답할 수 있는 선택 질문 하나를 둡니다.

## 후보 설명과 비교 출력

숙소명만 나열하지 않습니다. 각 후보에 분위기·강점·잘 맞는 여행자를 요약한 **한 줄 설명**을 붙이고, 동일한 날짜·인원·객실 수 기준의 비교표로 보여줍니다.

숙소 비교표에는 최소한 다음을 포함합니다.

- 숙소명, 한 줄 설명, 권역
- 1박 요금과 세금·봉사료를 포함한 예상 총액
- 가장 가까운 역·정류장까지의 실제 도보와 핵심 일정까지의 위치·접근
- 객실 크기·침대·정원과 수영장, 조식, 세탁, 피트니스 등 주요 시설·서비스
- 체크인·체크아웃, 짐 보관, 무료 취소·선결제 조건
- 반복 후기 경향에서 확인한 장점·주의점
- `위치`, `가격`, `시설`, `가족·커플·혼자`처럼 추천 대상과 선택 포인트

가격 또는 시설을 확인하지 못했으면 `확인 필요`로 표시합니다. 표 아래에는 가장 균형적인 추천을 밝히되 자동 확정하지 않고, 사용자에게 후보 번호나 숙소명을 고르는 선택 질문 하나를 둡니다.

## 조사 절차

1. 먼저 관광·업무·식사 권역과 공항·역 접근을 기준으로 2~4개 숙박 권역을 비교하고 권역 차이를 설명합니다.
2. 후보를 찾을 때 객실 정원과 침대 구성이 실제 인원을 수용하는지 확인합니다.
3. 같은 통화와 같은 숙박 수로 객실료, 세금, 봉사료, 리조트피, 청소비를 합친 총액을 비교합니다.
4. 무료 취소 기한, 선결제, 환불 불가, 보증금, 현장 결제 통화를 분리합니다.
5. 체크인·체크아웃, 24시간 프런트, 이른 체크인, 늦은 체크아웃, 전후 짐 보관 가능성을 확인합니다.
6. 가장 가까운 역·정류장, 실제 도보 환경, 택시 승하차, 엘리베이터·계단, 야간 귀가 안전성을 봅니다.
7. 여행의 핵심 장소까지의 대표 이동 시간과 환승을 비교하고 숙박비 절감이 교통비·피로 증가로 상쇄되는지 판단합니다.
8. 공식 시설 정보와 최근 후기 경향을 구분하고, 소음·청결·공사·조식 혼잡 같은 반복 이슈는 단정하지 않고 경향으로 기록합니다.
9. 최종 추천은 위치 우선, 가격 우선, 시설 우선처럼 선택 이유가 다른 2~4개로 좁힙니다.

## 최신성 및 근거

- 객실 재고, 가격, 세금, 취소 조건은 검색 시점과 채널에 따라 달라지므로 기준 시각을 표시합니다.
- 호텔 공식 사이트의 정책·시설을 우선하고 예약 채널은 실제 날짜의 가격·재고 비교 근거로 사용합니다.
- 지도 근거로 역·정류장과 핵심 권역까지의 위치를 확인합니다.
- 후기 정보는 최근성과 반복성을 함께 보고 사실 정보와 섞지 않습니다.
- 사용자 예약은 `booked`로 유지하며 더 싼 후보를 발견해도 자동으로 변경 대상으로 취급하지 않습니다.

### 기존 실데이터 수집 도구 재사용

사용자가 실제 숙소 가격·객실 수집을 요청하고 기존 로컬 수집 도구를 사용할 수 있으면 `../travel-planner/references/real_data_collection.md`와 `../travel-planner/tools/travel-planner-cli/README.md`를 읽습니다. 서버가 실행 중이면 Playwright 기반 `POST /collect`, 서버 없이 단독 실행할 때는 CLI `collect`를 사용할 수 있습니다. 날짜·인원·객실·무료 취소 조건이 검색 URL과 원문 요금 규정에 실제 반영됐는지 다시 확인하고, 자동화 차단·로그인·개인화 가격·사이트 약관 제한을 따릅니다. 현재 runtime의 공식 웹·예약 조회 도구가 더 직접적이면 그 경로를 우선합니다.

## DomainResult 반환 계약

독립 답변은 권역 비교와 한 줄 설명이 있는 숙소 비교표를 먼저 제공합니다. 오케스트레이션 작업에서는 다음 `DomainResult` 의미를 보존합니다.

```yaml
domain: lodging
status: ready | partial | blocked | skipped
freshness: current | stale
input_revision: 1
as_of: 2026-09-17T10:00:00+09:00
facts: []
candidates: []
recommendation: null
assumptions: []
conflicts: []
unresolved_questions: []
evidence:
  - source_type: official | booking | map | review | user
    source: "URL 또는 사용자 제공 예약"
    retrieved_at: 2026-09-17T10:00:00+09:00
    confidence: high | medium | low
costs:
  - amount: 0
    currency: KRW
    basis: per_room | per_night | per_group | total
    tax_included: true | false | unknown
    status: confirmed | estimated | variable | optional
```

각 후보에는 숙소명, 한 줄 설명, 권역, 객실·정원, 숙박 수, 1박과 총액, 세금 포함 여부, 취소·결제, 체크인·짐 보관, 교통 접근, 주요 시설·서비스, 추천 대상, 선택 포인트, 장점·주의점, 예약 상태를 둡니다.

## 완료 및 실패 조건

- 인원과 날짜에 맞는 후보가 동일 비용 기준으로 비교되고 권역·동선 추천 이유가 있으면 `ready`입니다.
- 실제 객실가나 일부 정책을 확인하지 못했지만 권역과 유효 후보를 제시할 수 있으면 `partial`입니다.
- 날짜·인원 없이 실제 객실 검색만 요구했거나 접근 차단으로 후보를 검증할 수 없으면 `blocked`입니다.
- 요청 범위가 아니면 `skipped`입니다.
- 예약·결제·로그인·개인정보 입력은 수행하지 않습니다.
- 날짜, 인원, 객실 수, 핵심 권역 또는 확정 일정이 바뀌면 이전 결과의 `freshness: stale`을 표시하고 다시 확인합니다.
