# 확정 게이트와 시각화 산출물
이 문서는 여행 계획 초안이 충분히 정리되었고, 추가 확인 항목이나 수정 요청이 없는 상태에서 예약 전 예상 일정, 예약 후 실행 일정, HTML 시각화 산출물로 마무리할 때 읽는다.

## 1. 확정 게이트
초안 작성 후 아래 상태를 확인한다.

- 필수 확인 질문이 남아 있는지
- 사용자가 수정하거나 제외하고 싶은 장소/식당/숙소/교통수단이 있는지
- 예약 전 단계인지 예약 후 실행 단계인지
- 날짜, 동행 유형, 여행 목적, 이동수단, 숙소, 예산 가정이 명확히 표시되었는지
- 날씨, 영업시간, 항공/배/열차, 비상정보처럼 최신 확인이 필요한 항목이 표시되었는지

확인할 내용이 남아 있으면 먼저 짧게 묻는다.
확인할 내용이 없고 수정사항도 없으면 바로 파일을 만들지 말고 문서화 여부를 묻는다. 예약이 없어도 예상 일정으로 문서화할 수 있다.

예시:

```markdown
현재 기준으로 추가 확인이 꼭 필요한 항목은 없습니다.
예약 전 상태이므로 이 내용을 `예상 일정안`으로 Markdown 문서화할까요?
원하면 같은 내용을 Day별 지도/타임라인이 있는 HTML 화면으로도 만들 수 있습니다.
```

예약 후 확정 정보가 충분하면 아래처럼 묻는다.

```markdown
현재 기준으로 추가 확인이 꼭 필요한 항목은 없습니다.
이 내용으로 `실행 일정표`를 Markdown 문서로 저장할까요?
원하면 같은 내용을 Day별 지도/타임라인이 있는 HTML 화면으로도 만들 수 있습니다.
```

## 2. 산출물 단계
산출물은 아래 순서로 만든다.

1. **Markdown 원본**: 여행 조건, 확정/미정/가정, 날짜별 예상 또는 실행 일정, 비용, 대체안, 준비물, 비상정보를 담은 기준 문서
2. **HTML 시각화본**: Markdown 내용을 바탕으로 모바일/데스크톱에서 보기 좋은 Day별 화면, 지도, 타임라인, 비용 요약을 보여주는 2차 산출물

Markdown을 먼저 만든다. HTML은 Markdown의 내용을 재구성한 표현물로 보고, 두 파일의 핵심 정보가 어긋나지 않게 한다.

## 3. 저장 경로
Markdown:

- `publish/travel/[국가명또는국내]/[도시명]_[n]박[m]일_기획안.md`
- `publish/travel/[국가명또는국내]/[도시명]_[n]박[m]일_예상일정.md`
- `publish/travel/[국가명또는국내]/[도시명]_[YYYYMMDD-YYYYMMDD]_실행일정.md`

HTML:

- `publish/travel/[국가명또는국내]/[도시명]_[n]박[m]일_시각화.html`
- `publish/travel/[국가명또는국내]/[도시명]_[YYYYMMDD-YYYYMMDD]_시각화.html`

같은 여행의 Markdown과 HTML은 파일명 접두어를 맞춘다.

## 4. HTML 시각화 구성
HTML은 단순 문서 복사가 아니라 여행 중 휴대폰으로 빠르게 보는 UI로 만든다.

HTML 파일을 새로 만들 때는 먼저 `references/html_visualization_pattern.md`를 읽고 `assets/html/day_route_visualization_sample.html`의 구조를 재사용한다. 기존 마라도, 대마도, 타이베이 산출물처럼 즉석으로 새 구조를 만들 수는 있지만, 특별한 이유가 없으면 샘플의 정보 순서와 컴포넌트 이름을 우선한다.

필수 영역:

- 타이틀 hero: 나라/지역/계절/예상 날씨에 맞춘 대표 이미지, 오버레이, 색상 테마
- 상단 요약: 여행지, 날짜, 동행 유형, 여행 목적, 날씨 기준, 예산 요약
- Day 탭: `Day 1`, `Day 2`, `Day 3`처럼 날짜별 전환
- 지도 패널: 해당 날짜의 숙소, 관광지, 식당, 쇼핑지, 공항/역/항구와 Day별 루트 표시
- 루트 검증: Google Maps 길찾기 링크, 방문 순서, 예상 이동시간, 최적성 판단, 대체 순서
- 타임라인: 시간, 시작 위치, 종료 위치, 이동/활동, 소요, 비용, 예약 상태
- 이동 요약: 하루의 주요 루트와 예상 이동수단
- 비용 요약: 확정/예상/선택 경비
- 대체안: 우천, 피로, 예약 실패, 교통 지연 시 선택지
- 체크리스트: 준비물, 예약 확인, 비상 연락망

## 5. 지도 표현 기준
- 정확한 좌표가 확인된 장소만 지도에 점으로 표시한다.
- 좌표가 불확실하면 임의로 찍지 말고 Google Maps, Naver Map, Kakao Map, OpenStreetMap 검색 링크를 제공한다.
- 외부 지도 API 키가 없으면 지도 이미지를 억지로 만들지 않는다.
- 인터넷 연결이 가능한 HTML이면 Leaflet + OpenStreetMap 타일을 사용할 수 있다. 이 경우 외부 타일 로딩이 필요하다고 표시한다.
- 완전 오프라인 HTML이 필요하면 지도 대신 Day별 장소 카드와 지도 검색 링크를 제공한다.
- 경로선은 실제 좌표와 방문 순서가 검증된 경우에만 그린다.
- 지도 패널은 개별 장소 핀만 보여주지 말고, Day별 `출발지 -> 경유지 -> 도착지` 순서를 함께 보여준다.
- 사용자가 현지 동선 최적화를 원하면 집에서 출국 공항/역/항구까지의 접근 구간은 지도 루트에서 제외하고, 목적지 공항/역/항구 도착 이후 또는 숙소 출발 이후부터 표시한다.
- Google Maps 길찾기 링크는 Day별로 1개 이상 제공한다. 좌표가 없으면 공식 장소명과 도시명을 넣은 Directions 링크 또는 검색 링크로 대체한다.
- 루트가 여러 개 가능하면 `추천 루트`, `조건부 루트`, `비추천/제외 루트`를 나눠 이동시간, 짐 부담, 영업시간, 식사 리듬 관점에서 판단한다.
- 좌표가 검증된 경우에만 지도 위 경로선을 그리고, 검증 전에는 링크와 방문 순서 카드로 표현한다.

## 6. UI/UX 기준
- 모바일에서 먼저 잘 읽히게 만든다.
- Day 탭은 상단에 고정하거나 쉽게 접근되게 둔다.
- 지도와 타임라인은 같은 Day 안에서 나란히 보이거나 모바일에서는 위아래로 쌓는다.
- Day별 첫 화면에는 해당 날짜의 루트 요약과 길찾기 버튼이 먼저 보이게 한다.
- HTML의 기본 정보 흐름은 `hero -> summary-grid -> decision-band -> tabs -> day-panel -> cost -> fallback -> checklist`로 둔다.
- 예약 확정 항목, 확인 필요 항목, 대체안을 색상/배지로 구분한다.
- 하루 일정은 너무 긴 표만 쓰지 말고 카드형 타임라인으로도 읽히게 한다.
- 공항/역/숙소/식당/관광/쇼핑은 아이콘이나 라벨로 구분한다.
- 색상은 과하게 화려하게 하지 말고, 나라/지역/계절/날씨를 반영하되 여행지 사진이 없어도 읽기 좋은 중립 톤과 충분한 대비를 유지한다.
- 타이틀 이미지는 실제 여행지, 계절, 목적이 드러나는 이미지를 우선하고, 국기나 추상 배경만으로 첫 화면을 구성하지 않는다.
- 사용자가 인쇄하거나 공유할 수 있도록 불필요한 애니메이션은 피한다.

## 7. HTML 생성 전 확인
HTML은 Markdown 확정 후 아래 중 필요한 것만 확인한다.

- 지도까지 포함할지, Day별 타임라인만 만들지
- 집에서 공항/역/항구까지 포함할지, 목적지 도착 이후 현지 루트만 볼지
- 나라/지역/계절/예상 날씨에 맞는 타이틀 이미지와 색상 테마를 자동 선택해도 되는지
- 외부 지도 타일/링크 사용이 괜찮은지
- 좌표 확인이 필요한지
- 모바일 중심인지, 인쇄/공유용인지

사용자가 "알아서 보기 좋게"라고 하면 나라/지역/계절/예상 날씨에 맞는 `tripData.theme`을 먼저 정한 뒤, 모바일 중심 Day 탭 + 현지 루트 요약 + Google Maps 길찾기 링크 + 타임라인 방식으로 만들고, 기준 샘플의 데이터 구조를 실제 여행 데이터로 교체한다.
