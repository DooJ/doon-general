# Microcopy Patterns

제품 문구, UX writing, empty/loading/error/success 메시지, 온보딩 문구를 작성하거나 리뷰할 때 사용한다. 화면 흐름은 대체로 정해졌지만 사용자가 무엇을 해야 하는지 문구로 명확히 해야 할 때 읽는다.

## 1. Voice And Tone

| 항목 | 정의 |
|---|---|
| 브랜드 성격 | 예: 전문적, 친근함, 빠름 |
| 사용자 상황 | 예: 처음 사용, 반복 업무, 오류 복구, 결제 전 |
| 금지 톤 | 예: 과장, 장난스러움, 단정적 표현 |
| 용어 원칙 | 사용자 언어 우선, 내부 코드명 금지 |

톤 조절:

- 위험하거나 민감한 상황에서는 친근함보다 명확성과 책임감을 우선한다.
- 반복 업무 화면에서는 개성보다 스캔 가능성과 일관성을 우선한다.
- 신규 사용자 온보딩에서는 다음 행동을 짧고 직접적으로 말한다.

## 2. 상태별 문구 패턴

| 상태 | 포함할 내용 | 예시 구조 |
|---|---|---|
| Empty | 현재 상태, 가능한 다음 행동, 필요 시 예시 | “아직 {대상}이 없습니다. {행동}해 시작하세요.” |
| Loading | 기다리는 대상, 오래 걸릴 수 있는 이유 | “{대상}을 불러오는 중입니다.” |
| Success | 완료 사실, 다음 선택지 | “{작업}이 완료되었습니다. {다음 행동}할 수 있습니다.” |
| Error | 원인, 영향, 복구 행동 | “{원인}으로 {작업}을 완료하지 못했습니다. {행동}해 주세요.” |
| Permission | 접근 불가 이유, 요청 경로 | “이 기능은 {권한}이 필요합니다. {관리자/설정}에서 요청하세요.” |
| Destructive | 영향, 되돌림 가능성, 확인 대상 | “{대상}을 삭제하면 {영향}이 발생합니다. {복구 가능 여부}.” |

## 3. CTA와 버튼

| 목적 | 좋은 패턴 | 피할 표현 |
|---|---|---|
| 생성 | “새 {대상} 만들기” | “확인”, “처리” |
| 저장 | “변경사항 저장” | “완료”만 단독 사용 |
| 삭제 | “{대상} 삭제” | “OK”, “진행” |
| 재시도 | “다시 시도” | “새로고침”만으로 원인 미표시 |
| 권한 요청 | “권한 요청” | “문의하기”만 단독 사용 |

## 4. 오류 문구 점검

오류 메시지는 가능하면 다음 순서를 따른다.

1. 무엇이 안 됐는지 말한다.
2. 사용자가 알 수 있는 원인을 말한다.
3. 지금 할 수 있는 행동을 말한다.
4. 필요하면 지원 요청에 필요한 정보를 남긴다.

피해야 할 문구:

- “알 수 없는 오류가 발생했습니다”만 단독 사용
- “잘못된 접근입니다”처럼 사용자를 탓하는 표현
- “관리자에게 문의하세요”만 있고 어떤 정보를 전달해야 하는지 없는 표현

## 5. 리뷰 체크리스트

- 문구만 읽어도 다음 행동을 알 수 있는가?
- 버튼과 결과 문구의 동사가 일치하는가?
- 내부 용어, 개발자 용어, 브랜드 과장이 섞이지 않았는가?
- 번역이나 길이 확장 시 UI를 깨뜨릴 위험이 있는가?
- 금융, 건강, 법률, 개인정보 영역에서 과장 또는 확정 표현을 피했는가?
