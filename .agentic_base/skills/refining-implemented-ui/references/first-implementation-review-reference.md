# 최초 적용 사례 레퍼런스

## 사례의 범위

최초 적용 사례에서는 1차 기능 개발이 끝난 여러 운영 표면을 화면 캡처 대신 실제 소스와 데이터 집계에 근거한 정적 리뷰 스튜디오로 재구성했다. 전체 구조에서 세부 화면·목록·설정·전체보기로 내려가며 순차 확정했고 마지막에 세부 확정안을 합친 통합 화면을 만들었다.

## 일반화할 교훈

### 전체와 세부를 왕복한다

전체 구조를 먼저 정한 뒤 세부 파트를 리뷰한다. 세부 확정안이 기존 전체 화면에 자동으로 보존된다고 가정하지 않고 마지막 통합 단계에서 모두 다시 합친다.

### 기준본을 계속 볼 수 있게 한다

세부 화면을 크게 그리거나 모바일로 바꿀 때도 기존 전체 구조와 비교 가능한 기준본을 유지해야 사용자가 수정 범위를 판단할 수 있다.

### 문서 기록만으로 확정하지 않는다

사용자 의견을 글로만 적어두지 않고 실제 수정안 화면에 반영한 뒤 확정한다. 이것이 개발 전 누락을 줄이는 핵심이다.

### 선택 맥락을 유지한다

review unit, 사용자 역할, 기준본/수정안, desktop/mobile을 전환해도 비교 선택이 불필요하게 초기화되지 않아야 한다.

### mobile은 portrait desktop이 아니다

휴대폰에서는 desktop sidebar를 상단에 붙이지 않고 hamburger와 drawer로 바꾸며, 좌우 배치는 위아래로 재구성하고 scroll owner와 sticky 영역을 다시 정했다.

### 실제 데이터의 모양을 반영한다

실제 고객 원문은 쓰지 않으면서 매장·장비·리뷰 총량, 긴 리뷰 길이, media 유무 같은 데이터 특성을 합성 장면에 반영했다.

### 리뷰 환경을 계속 접근 가능하게 한다

사용자가 순차 리뷰하는 동안 같은 로컬 URL에서 스튜디오를 계속 볼 수 있어야 한다. 화면 수정과 대화가 반복되는 작업에서는 preview server의 생명주기도 리뷰 경험의 일부다.

### 최종본 이후 actual 비교가 필요하다

리뷰 스튜디오의 최종 통합안은 개발 지시의 기준이며, 실제 운영 화면 수정 뒤 같은 role·viewport·state로 다시 비교해야 작업이 닫힌다.

## HTML 예제 장면 연결

[Self-contained 리뷰 스튜디오 예제](../assets/examples/review-studio-sample.html)는 이 사례에서 일반화한 구조를 네 장면으로 보여준다.

| 예제 장면 | 확인할 원칙 |
|---|---|
| 데스크톱 | 전체 구조, sidebar, 역할별 요약, 상세 맥락, 주요 작업 영역의 밀도 |
| 모바일 | desktop 축소가 아닌 hamburger, 위아래 재배치, scroll owner, pagination |
| 기준본 ↔ 수정안 | immutable baseline, proposal revision, 의견 출처, decision ID 연결 |
| 최종 통합본 | confirmed decision coverage, final 위치, actual parity, 열린 누락 0건 |

예제의 운영 콘솔 도메인과 시각 스타일은 설명용이다. 다른 프로젝트에서는 navigation, 권한, breakpoint, 데이터 구조를 다시 조사하고 예제를 그대로 복제하지 않는다.

## 복제하지 않을 항목

다음은 최초 적용 사례에만 해당하므로 다른 프로젝트에 기본값으로 쓰지 않는다.

- 특정 웹·앱 surface 이름
- 최초 사례의 도메인 객체와 분류 구조
- 특정 리뷰 단위 번호와 화면 수
- 1600×1000, 1920×1080 같은 특정 프레임 크기
- 사용자와 슈퍼 관리자라는 역할명
- 프로젝트의 fixture 수치와 상태 문구

다른 프로젝트에서는 반드시 실제 navigation, 권한 정책, breakpoint, 데이터 schema를 다시 조사한다.
