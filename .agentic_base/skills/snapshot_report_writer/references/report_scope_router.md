# 리포트 범위 라우터
스냅샷 리포트 요청은 먼저 부분 리포트인지 전체 리포트인지 분류한다.

## 범위 분류
| 범위 | 사용자 표현 | 보고 초점 | 산출 방식 |
|---|---|---|---|
| 부분 리포트 | 이 기능 분석 보고서, 이 API 딥다이브, 이 장애 원인, 이 리팩토링 제안 | 특정 기능, 화면, API, 장애, 모듈, 결정 | 단일 주제 보고서 |
| 전체 리포트 | 이 프로젝트 분석 보고서, 전체 상태 보고, 릴리즈 준비도, 기술부채 전체 리뷰 | 프로젝트 전체 구조, 상태, 리스크, 준비도, 운영/QA/보안 | 단일 종합 보고서 또는 보고서 세트 |
| 의사결정 리포트 | ADR, 선택지 비교, 도입 검토 | 특정 결정 시점의 맥락과 선택 근거 | ADR 또는 제안서 |
| 사후 리포트 | 포스트모템, 장애 회고, 릴리즈 회고 | 특정 사건의 원인, 영향, 재발 방지 | 포스트모템 |

## 판별 규칙
1. 사용자가 기능, 화면, API, 파일, 장애 번호처럼 대상을 좁히면 부분 리포트다.
2. 사용자가 프로젝트, 서비스, 앱, 전체 구조, 전체 상태, 준비도라고 말하면 전체 리포트다.
3. 사용자가 날짜별 기록, 분석 보고서, 제안서, ADR을 원하면 snapshot report다.
4. 사용자가 "항상 최신으로 유지"를 원하면 living doc이 더 적합하다.
5. 하나의 요청에 시점 보고와 최신 문서 갱신이 함께 있으면 보고서를 먼저 만들고 `Living Docs 반영 후보`를 남긴다.

## 질문 예시
```markdown
보고 범위가 두 가지로 갈립니다.

- 부분 리포트: 특정 기능/장애/API를 깊게 분석
- 전체 리포트: 프로젝트 전체 구조, 상태, 리스크, 준비도를 분석

현재 표현상 전체 리포트가 맞아 보입니다. 이 범위로 작성하겠습니다.
```
