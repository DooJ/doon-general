# 문서별 품질 기준
문서가 많아도 내용이 얇으면 실패다. 각 문서는 개발, 디자인, QA, 인수인계 중 하나 이상의 실제 행동으로 이어져야 한다.

## 공통 필수 섹션
모든 주요 문서는 아래 요소를 포함한다.

- 목적
- 범위
- 근거 자료
- 확정 사항
- 가정
- 미정 및 사용자 확인 필요
- 관련 문서 또는 관련 코드
- 갱신 트리거
- 검증 방법

## 프로젝트 정의서
- 배경과 문제 정의
- 목표 사용자
- 핵심 가치 제안
- 성공 기준
- POC 필요 여부와 검증 가설
- MVP 범위
- PRD 상태와 작성/지연 사유
- 제외 범위
- 주요 리스크
- 의사결정이 필요한 항목

## 아이디어 브리프
- 아이디어 한 줄 정의
- 배경과 문제 의식
- 핵심 사용자 가설
- 핵심 가치 가설
- 기존 대안
- 검증해야 할 가설
- 개발 착수 전 필요한 결정

## 디자인 기획 문서
- 디자인 맥락
- UX 포지셔닝
- 디자인 방향 후보 2개 이상
- 후보별 장점, 단점, 맞는 이유, 안 맞는 이유
- 레퍼런스 분석
- 추천 방향
- 버린 방향과 이유
- 프로토타입 검증 계획

## 요구사항 정의서
- PRD 상태: draft, active, deferred
- 기능 요구사항 표
- 비기능 요구사항
- 권한과 역할
- 정책과 제약
- 예외와 오류 조건
- 기능별 acceptance criteria
- MVP, 2차, 제외 범위 구분

## POC 계획
- 검증할 가설
- 가장 위험한 가정
- 최소 실험 범위
- 성공 기준
- 중단 기준
- 수집할 증거
- POC 이후 의사결정

## PRD
- 제품 문제
- 목표와 non-goals
- 대상 사용자와 주요 시나리오
- 기능 요구사항
- 비기능 요구사항
- 정책과 제약
- release criteria
- open questions

## 사용자 시나리오
- 페르소나 또는 사용자 유형
- 주요 사용자 여정
- 단계별 사용자 목표
- 성공 흐름
- 실패 흐름
- 재시도와 복구 흐름
- 시나리오별 관련 화면

## 기능 카탈로그
- 기능군 목록
- 기능별 사용자 또는 시스템 목적
- 주요 진입점
- 구현 상태: 구현됨, 부분 구현, 미확인, 제거 후보
- 관련 화면, API, 배치, 데이터 모델
- 관련 코드 경로
- 관련 리빙독
- 확인한 근거와 미확인 사항

## 화면 명세서
- 화면 목록과 우선순위
- 각 화면의 목적
- 입력 항목과 검증 규칙
- 주요 버튼과 인터랙션
- 화면 전환
- 빈 상태, 로딩, 오류, 성공, 권한 부족 상태
- 모바일/데스크톱 차이

## 디자인 문서
- 디자인 목표와 원칙
- 정보 구조
- 레이아웃 원칙
- 색상, 타이포그래피, 간격 방향
- 컴포넌트 목록
- 컴포넌트 상태: default, hover, focus, disabled, loading, error
- 반응형 기준
- 접근성 기준
- 구현 handoff 기준

## 기술 설계서
- 전체 구조 요약
- 레이어와 모듈 책임
- 핵심 데이터 흐름
- 상태 관리 방식
- 에러 처리와 재시도
- 인증/권한 처리
- 외부 연동 방식
- 선택한 기술과 선택하지 않은 대안
- 확장과 되돌림 전략

## 시스템 구성 문서
- 클라이언트, 서버, DB, 저장소, 외부 시스템 구성
- 환경별 구성: local, staging, production
- 배포 단위
- 설정과 비밀값 관리 기준
- 로그와 모니터링
- 장애 대응 연결 지점

## 데이터 모델
- 엔티티 목록
- 필드 정의
- 관계
- 상태값
- 제약 조건
- 생성, 조회, 수정, 삭제 정책
- 보존과 삭제 정책

## API 명세서
- API 목록
- 인증 방식
- request/response 스키마
- 에러 코드
- 권한 조건
- 페이지네이션, 정렬, 필터
- 멱등성 또는 중복 요청 처리
- 예시 payload

## 개발 일정
- 마일스톤
- 작업 분해
- 우선순위
- 선행 조건
- 담당 영역
- 리스크와 대응
- 검증 기준
- 출시 판단 기준

## QA 문서
- 핵심 흐름별 체크리스트
- 화면별 체크리스트
- 권한별 체크리스트
- 입력값 경계 조건
- 오류와 복구
- 브라우저/기기/해상도 범위
- 회귀 테스트 범위
- 릴리즈 전 최종 확인 항목

## 의사결정 문서
- 현재 결론
- 결정 배경과 문제
- 선택한 대안
- 버린 대안과 이유
- 근거 문서, 회의, 코드 링크
- 남은 이견
- 되돌릴 조건 또는 재검토 조건
- 다음 갱신 트리거

## 진행 상태 문서
- 현재 한 줄 요약
- 완료된 일
- 진행 중인 일
- 막힌 일과 원인
- 다음 행동
- 사용자 확인 필요
- 리스크와 대응
- 마지막 확인 기준

## 운영/배포 문서
- 대상 환경
- 필수 설정과 비밀값 관리
- 배포 절차
- 배포 후 검증
- 롤백 절차
- 로그와 모니터링
- 장애 분류와 초기 대응
- 운영자가 반복 수행하는 작업

## 온보딩/인수인계 문서
- 처음 읽을 순서
- 프로젝트 목적과 주요 사용자
- 로컬 실행 방법
- 테스트와 검증 명령
- 주요 모듈과 진입점
- 흔한 실패와 해결
- 변경 시 주의할 위험 지점
- 현재 남은 작업과 담당 영역

## 사용자/서비스 문서
- 대상 사용자
- 사용 전제 조건
- 핵심 작업별 절차
- 화면 또는 기능별 설명
- 자주 묻는 질문
- 알려진 문제와 우회 방법
- 지원 또는 에스컬레이션 기준
- 사용자에게 공개해도 되는 표현인지 점검

## 데이터/보안/정책 문서
- 데이터 항목과 의미
- 수집 출처
- 민감도와 접근 권한
- 보관, 백업, 삭제, 파기 기준
- 인증과 권한 모델
- 로그 노출 금지 항목
- 감사 또는 추적 필요 항목
- 사용자 확인 또는 법무 확인 필요

## 디자인 시스템/콘텐츠 문서
- 적용 범위
- 컴포넌트 또는 토큰 목록
- 상태별 동작과 시각 기준
- 사용 금지 패턴
- 접근성 기준
- 문구 톤과 금지 표현
- 오류, 빈 상태, 성공, 로딩 문구
- 구현/검수 기준

## 비즈니스/성과 문서
- 대상 고객과 가치
- 수익 또는 비용 구조
- 가격 정책과 예외
- KPI 정의와 계산식
- 이벤트 이름과 속성
- 수집 위치와 책임
- 해석 주의사항
- 실험 또는 변경 기준

## 문서 운영 문서
- 문서 구조와 읽는 순서
- 문서별 소유 영역
- 관련 문서 연결
- 용어 정의
- 오래된 문서와 대체 문서
- 삭제, 보류, 갱신 기준

## 얇은 문서 방지 규칙
- 제목과 일반론만 있는 문서는 만들지 않는다.
- "추후 작성"만 반복하지 않는다. 모르면 `미정`에 이유와 필요한 결정을 적는다.
- 같은 내용을 여러 문서에 복사하지 않는다. 문서별 책임을 나누고 관련 문서로 연결한다.
- 확정되지 않은 기능을 확정 요구사항처럼 쓰지 않는다.
- QA 문서는 요구사항과 화면 명세를 실제로 검증할 수 있어야 한다.
